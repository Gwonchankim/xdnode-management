# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev            # vinext dev (local Cloudflare Worker + D1 simulation)
npm run build           # vinext build
npm run start           # vinext start (serve built output)
npm run lint             # eslint . --ignore-pattern dist --ignore-pattern .next
npm test                 # npm run build, then node --test over an explicit list of tests/*.test.mjs
npm run db:generate      # drizzle-kit generate (writes drizzle/NNNN_*.sql from db/schema.ts)
npm run assistant:claude # local Claude CLI bridge for the in-app AI assistant (127.0.0.1:3130)
npm run resume:bridge    # local Claude CLI bridge for HR resume analysis (127.0.0.1:3120)
npm run assistant:bridge # legacy Codex CLI assistant bridge (127.0.0.1:3110), kept for rollback
```

`npm test` does **not** glob — it runs the test files listed by name in the `package.json` `test` script. A new `tests/*.test.mjs` file must be added to that list or `npm test` won't run it.

Test files are plain `node --test` files, so run one directly, e.g. `node --test tests/erp-platform.test.mjs`. Most tests read source files as text and don't need a build. `tests/rendered-html.test.mjs` needs `npm run build` first. `tests/helpers/hr-api-harness.mjs` loads real route files through a TypeScript loader hook and runs them against an in-memory `node:sqlite` database standing in for D1. Use it for behavioral route tests (see `tests/hr-api-integration.test.mjs`).

## Stack

Next.js-shaped app router code (`app/`) served through **vinext** (Cloudflare's Next-compatible framework), deployed as a Cloudflare Worker with a D1 (SQLite) database and an R2 bucket (`HR_AUDIO`). `.openai/hosting.json` declares the D1/R2 binding names (`d1`, `r2`); `vite.config.ts` reads that file and simulates the bindings locally via `@cloudflare/vite-plugin`. `worker/index.ts` is the actual Worker entry point — it wraps vinext's app-router handler, adds security headers, and handles the `/_vinext/image` image-optimization route.

## Architecture

This is a single Korean-language ERP application ("XD NODE") for one company, not a generic starter — despite the `site-creator-vinext-starter` package name (leftover from the template this was bootstrapped from).

**Frontend shell.** [app/page.tsx](app/page.tsx) is a large (1500+ line) client component that is effectively the whole app shell: it switches between top-level modules (`finance`, `sales`, `hr`, `compensation`) and renders one of ~25 `*-workspace.tsx` / `*-view.tsx` components per module/screen. There is very little server-side routing — most navigation is client-side state (`useState`), not Next `Link`/route segments. `app/incentive/` is the one exception: a standalone routed page outside the SPA shell.

**API routes.** Each `app/api/<module>/<feature>/route.ts` is self-contained: it exports `GET`/`POST`/`PUT`/`DELETE`, and near-universally follows this pattern:
1. `ensureSchema()` — runs `CREATE TABLE IF NOT EXISTS` / index statements via `db.batch(...)`. There is no separate migration-apply step at runtime; the `drizzle/NNNN_*.sql` files under [drizzle/](drizzle/) are a historical record generated by `drizzle-kit generate`, but the actual runtime schema is created idempotently inline in each route file.
2. `authorizeErpRequest(db, module, action)` from [app/erp-platform.ts](app/erp-platform.ts) — resolves the caller's identity, employee record, and role, and checks `module:action` permission. Returns either `{ principal }` or `{ response }` (a ready-to-return 401/403 `Response`) — callers check `authorization.response` first.
3. Business logic via raw `db.prepare(...).bind(...).all()/.first()/.run()` (D1's native API), not the Drizzle query builder.
4. `writeErpAudit(db, { principal, module, action, entityType, entityId, before, after })` on every mutation, for the audit trail.

**Authorization model** ([app/erp-platform.ts](app/erp-platform.ts)): roles are `SUPER_ADMIN | FINANCE_ADMIN | HR_ADMIN | RECRUITER | SALES_ADMIN | VIEWER`, permissions are `<module>:<action>` strings (`finance:write`, `hr:approve`, etc.) checked against a static `rolePermissions` map. A caller's identity comes from `app/chatgpt-auth.ts` (Sign-in with ChatGPT headers injected by the Dispatch hosting platform, see [README.md](README.md)), then matched to an HR employee record, then to an `erp_user_access` row for roles.

**Approvals.** [app/approval-engine.ts](app/approval-engine.ts) implements a multi-step, policy-driven approval workflow (`erp_approval_requests` / `_policies` / `_policy_steps` / `_steps` / `_events` / `_delegations` tables, all bootstrapped in `erp-platform.ts`'s `ensureErpPlatformSchema`). Feature routes call `createApprovalRequest(...)` when a record needs sign-off (e.g. budget plan submission in [app/api/finance/budget/route.ts](app/api/finance/budget/route.ts)) instead of implementing their own approval state machine.

**Drizzle.** [db/schema.ts](db/schema.ts) and [db/index.ts](db/index.ts) exist (used by `npm run db:generate`) but are not imported anywhere under `app/` — nothing in the running app uses the Drizzle query builder or `getDb()`. Treat `db/schema.ts` as a migration-authoring surface only; actual reads/writes happen through raw SQL in route files as described above.

**Data files.** [app/finance-current-data.ts](app/finance-current-data.ts) (~12k lines) and [app/hr-company-data.ts](app/hr-company-data.ts) embed real, dated business data (accounts, journal summaries, employee roster) for the company this ERP runs — not synthetic fixtures. `app/finance-historical-data.ts` / `finance-decision-model.ts` / `finance-time-series.ts` derive analytics from that data. Treat edits to these files as data-accuracy-sensitive, not just code changes.

**Local AI bridges.** The Worker can't spawn processes, so AI features call small Node HTTP servers in `scripts/` that wrap the `claude` CLI and run on the desktop. [app/api/assistant/route.ts](app/api/assistant/route.ts) proxies to `CLAUDE_ASSISTANT_BRIDGE_URL`, which defaults to `http://127.0.0.1:3130` (`scripts/claude-assistant-bridge.mjs`). The browser never calls the bridge directly, so other devices on the network can still use the assistant. The bridge validates model output against `scripts/codex-assistant-response-schema.json`, because `proposedActions` are change proposals the UI can apply to real ERP records. [app/api/hr/resume-analysis/route.ts](app/api/hr/resume-analysis/route.ts) calls `CLAUDE_BRIDGE_URL`, which defaults to `:3120` (`scripts/claude-resume-bridge.mjs`, an OpenAI-compatible `/chat/completions` shim). The bridges bind to localhost, cap request size, and handle one request at a time.

**Docs.** [docs/](docs/) contains one `*-plan.md` per feature area (finance, HR, sales, data-governance modules) describing intended behavior — check the relevant plan doc before changing a workspace's business rules.

## Conventions

- UI text and most identifiers/comments are Korean; currency is KRW (`Intl.NumberFormat("ko-KR", { style: "currency", currency: "KRW" })` / `formatWon` helpers). Keep new user-facing strings in Korean to match the rest of the app.
- `tests/*.test.mjs` mostly assert (via regex) that specific source files contain specific guardrails — e.g. that every sensitive API route calls both `authorizeErpRequest` and `writeErpAudit`, or that a specific SQL/UI string exists — rather than executing the app end-to-end. When adding a new mutating API route, check whether an existing test enumerates route files by name (see `tests/erp-platform.test.mjs`) and needs the new route added to its list.
- The repo root also holds a large number of untracked, non-source artifacts (`xdnode-erp-v*.tar.gz` snapshots, `council-report-*` / `council-transcript-*` files, `deliverables/`, `work_incentive/`, `tmp/`, `tmp_modelb_refresh/`, `.codex*-analysis/`, etc.) from prior working sessions. These are not part of the application and shouldn't be treated as architecture references or added to as a side effect of unrelated work.
