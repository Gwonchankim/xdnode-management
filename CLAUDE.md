# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev            # vinext dev (local Cloudflare Worker + D1 simulation)
npm run build           # vinext build
npm run start           # vinext start (serve built output)
npm run lint             # eslint . --ignore-pattern dist --ignore-pattern .next
npm test                 # npm run build, then node --test over an explicit list of tests/*.test.mjs
npm run db:generate      # drizzle-kit generate (writes drizzle/NNNN_*.sql from db/schema.ts)
npm run assistant:claude # local Claude CLI bridge for the in-app AI assistant (127.0.0.1:3130)
npm run resume:bridge    # local Claude CLI bridge for HR resume analysis (127.0.0.1:3120)
npm run assistant:bridge # legacy Codex CLI assistant bridge (127.0.0.1:3110), kept for rollback
```

`npm test` does **not** glob — it runs the test files listed by name in the `package.json` `test` script. A new `tests/*.test.mjs` file must be added to that list or `npm test` won't run it (`tests/removal-guards.test.mjs` fails when the list and the directory disagree).

Test files are plain `node --test` files, so run one directly, e.g. `node --test tests/erp-platform.test.mjs`. Most tests read source files as text and don't need a build. `tests/rendered-html.test.mjs` and `tests/bundle-exposure.test.mjs` need `npm run build` first. `tests/helpers/hr-api-harness.mjs` loads real route files through a TypeScript loader hook and runs them against an in-memory `node:sqlite` database standing in for D1. Use it for behavioral route tests (see `tests/hr-api-integration.test.mjs`).

## Stack

Next.js-shaped app router code (`app/`) served through **vinext** (Cloudflare's Next-compatible framework), written as a Cloudflare Worker with a D1 (SQLite) database and an R2 bucket (`HR_AUDIO`). `.openai/hosting.json` declares the D1/R2 binding names (`d1`, `r2`); `vite.config.ts` reads that file and simulates the bindings locally via `@cloudflare/vite-plugin`. `worker/index.ts` is the actual Worker entry point — it wraps vinext's app-router handler, adds security headers, and handles the `/_vinext/image` image-optimization route.

**How it actually runs.** The Cloudflare deployment was cancelled; production is the **vinext dev server on one office PC**, started by [scripts/Start-XDNodeERP.ps1](scripts/Start-XDNodeERP.ps1) (dev on `127.0.0.1:3000` plus the 3120/3130 bridges). The real D1/R2 data therefore lives in `.wrangler/state/` (Miniflare SQLite + blob files) — it is the live company database, not a disposable local cache. Don't delete or reset it. Inspect only copies: `scripts/verify-state-snapshot.mjs` refuses to open the live directory. `scripts/restore-known-data.mjs` re-seeds known values through the app API rather than writing to the DB directly, so audit and state-transition rules still apply.

**LAN-exposure guards (R0).** The dev server binding to `127.0.0.1` (not `0.0.0.0`), `X_LOCAL_EXPLORER = "false"` (the Miniflare explorer exposes an arbitrary-SQL API against D1), and `DEV_FS_DENY` in `vite.config.ts` (which must restate Vite's default deny patterns and anchor folder patterns to `PROJECT_ROOT`) are all pinned by [tests/lan-exposure-guards.test.mjs](tests/lan-exposure-guards.test.mjs). Don't loosen these without a plan change.

## Architecture

This is a single Korean-language ERP application ("XD NODE") for one company, not a generic starter — despite the `site-creator-vinext-starter` package name (leftover from the template this was bootstrapped from).

**Frontend shell.** [app/page.tsx](app/page.tsx) is a small client component that is the whole app shell: it switches between three tabs (`hr`, `compensation`, `audit`) and mounts `HRWorkspace` ([app/hr-workspace.tsx](app/hr-workspace.tsx), ~4,900 lines, rendered in a shadow root styled by `public/hr-workspace.css`, with its screens in `hr-*-view.tsx` / `*-view.tsx`), `CompensationCalculator`, or `AuditLogWorkspace`. Navigation is client-side state (`useState`), not Next `Link`/route segments. `app/incentive/` is the one exception: a standalone routed page outside the SPA shell.

**API routes.** Each `app/api/<module>/<feature>/route.ts` is self-contained: it exports `GET`/`POST`/`PUT`/`DELETE`, and near-universally follows this pattern:
1. `ensureSchema()` — runs `CREATE TABLE IF NOT EXISTS` / index statements via `db.batch(...)`. There is no separate migration-apply step at runtime; the `drizzle/NNNN_*.sql` files under [drizzle/](drizzle/) are a historical record generated by `drizzle-kit generate`, but the actual runtime schema is created idempotently inline in each route file.
2. `authorizeErpRequest(db, module, action)` from [app/erp-platform.ts](app/erp-platform.ts) — resolves the caller's identity, employee record, and role, and checks `module:action` permission. Returns either `{ principal }` or `{ response }` (a ready-to-return 401/403 `Response`) — callers check `authorization.response` first.
3. Business logic via raw `db.prepare(...).bind(...).all()/.first()/.run()` (D1's native API), not the Drizzle query builder.
4. `writeErpAudit(db, { principal, module, action, entityType, entityId, before, after })` on every mutation, for the audit trail.

**Authorization model** ([app/erp-platform.ts](app/erp-platform.ts)): roles are `SUPER_ADMIN | HR_ADMIN | RECRUITER | VIEWER`, modules are `hr | recruitment | settings`, and permissions are `<module>:<action>` strings (`hr:write`, `hr:approve`, `settings:admin`, etc.) checked against a static `rolePermissions` map. A caller's identity comes from `app/chatgpt-auth.ts`: Sign-in with ChatGPT headers when a hosting platform injects them (see [README.md](README.md)), otherwise the single local identity in `LOCAL_ERP_USER_EMAIL` / `LOCAL_ERP_USER_NAME`. That fallback is what the office-PC setup uses, so today every client is treated as the same person. The identity is then matched to an HR employee record, then to an `erp_user_access` row for roles.

**No approvals (direct apply).** The e-approval engine is gone (plan D2-개정). HR state changes that used to wait for sign-off (personnel actions, retirements, leave requests, payroll approval, performance finalization, workforce-plan approval, requisition opening) now apply immediately for a caller with the permission. The statement builders live in [app/hr-transitions.ts](app/hr-transitions.ts): pure functions returning `D1PreparedStatement[]`, guarded by `WHERE status IN (<from>, <legacy pending>)`; the route runs `db.batch` and returns 409 `CONFLICT` when `meta.changes` is 0. Rows left `SUBMITTED`/`PENDING` from the approval era are decided through the same buttons. The old `erp_approval_*`, finance and sales tables stay in the DB (never dropped, D4), but no code creates or reads them.

**Drizzle.** [db/schema.ts](db/schema.ts) and [db/index.ts](db/index.ts) exist (used by `npm run db:generate`) but are not imported anywhere under `app/` — nothing in the running app uses the Drizzle query builder or `getDb()`. Treat `db/schema.ts` as a migration-authoring surface only; actual reads/writes happen through raw SQL in route files as described above.

**Data files.** [app/hr-company-data.ts](app/hr-company-data.ts) embeds the real employee roster and pay seed — not synthetic fixtures — and is **server-only** (`import "server-only"`, so a client import fails the build). Client code imports the org/rank/title catalogs from `app/hr-company-catalogs.ts` and loads employees from `/api/hr/employee-records`; `tests/bundle-exposure.test.mjs` checks that no seed name, phone, email or salary reaches `dist/client`. Treat edits as data-accuracy-sensitive. The finance data files were removed from the tree (kept only in tag `erp-final-20260923` and an archive outside the repo).

**Local AI bridges.** The Worker can't spawn processes, so AI features call small Node HTTP servers in `scripts/` that wrap the `claude` CLI and run on the desktop. [app/api/assistant/route.ts](app/api/assistant/route.ts) proxies to `CLAUDE_ASSISTANT_BRIDGE_URL`, which defaults to `http://127.0.0.1:3130` (`scripts/claude-assistant-bridge.mjs`). The browser never calls the bridge directly, so other devices on the network can still use the assistant. The bridge validates model output against `scripts/codex-assistant-response-schema.json`, because `proposedActions` are change proposals the UI can apply to real ERP records. [app/api/hr/resume-analysis/route.ts](app/api/hr/resume-analysis/route.ts) calls `CLAUDE_BRIDGE_URL`, which defaults to `:3120` (`scripts/claude-resume-bridge.mjs`, an OpenAI-compatible `/chat/completions` shim). The bridges bind to localhost, cap request size, and handle one request at a time.

**Docs.** [docs/](docs/) contains one `*-plan.md` per HR/platform feature area describing intended behavior — check the relevant plan doc before changing a workspace's business rules. The finance, sales, data and master-impact plans are in `docs/archive/` for reference only.

**In-flight restructuring (`xdnode-management`).** [docs/00-pm/xdnode-management.prd.md](docs/00-pm/xdnode-management.prd.md), [docs/01-plan/features/xdnode-management.plan.md](docs/01-plan/features/xdnode-management.plan.md), and [docs/02-design/features/xdnode-management.design.md](docs/02-design/features/xdnode-management.design.md) describe a plan to rename the product "XDnode management" and turn it into a tool for the 경영지원실 (management support team). Its phases are real accounts/sessions with per-role tab visibility, then team chat, then a link to a quotation tool. Release R1 has **removed the finance and sales modules** and, per D2-개정, the approval engine as well. The audit trail (`writeErpAudit`) stays, and `app/incentive/` stays but no longer uses sales data. Git tag `erp-final-20260923` marks the last state that still contains finance, sales, and approvals. Before changing platform or shell code, check the plan/design docs for the current phase and decisions (numbered `D1`, `D2`, …, which code comments and tests reference).

## Conventions

- UI text and most identifiers/comments are Korean; currency is KRW (`Intl.NumberFormat("ko-KR", { style: "currency", currency: "KRW" })` / `formatWon` helpers). Keep new user-facing strings in Korean to match the rest of the app.
- `tests/*.test.mjs` mostly assert (via regex) that specific source files contain specific guardrails — e.g. that every sensitive API route calls both `authorizeErpRequest` and `writeErpAudit`, or that a specific SQL/UI string exists — rather than executing the app end-to-end. `tests/erp-platform.test.mjs` scans every `app/api/**/route.ts` and fails if a mutating one lacks either call; `tests/removal-guards.test.mjs` keeps the removed finance/sales/approval/data paths from coming back.
- The repo root also holds a large number of untracked, non-source artifacts (`xdnode-erp-v*.tar.gz` snapshots, `council-report-*` / `council-transcript-*` files, `deliverables/`, `analysis/`, `tools/`, root-level `*.py` workbook-analysis scripts, `.bkit/`, `work_incentive/`, `tmp/`, `tmp_modelb_refresh/`, `.codex*-analysis/`, etc.) from prior working sessions. These are not part of the application and shouldn't be treated as architecture references or added to as a side effect of unrelated work.
