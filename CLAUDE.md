# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev            # vinext dev on 127.0.0.1:3100 (local Cloudflare Worker + D1 simulation; never 0.0.0.0)
npm run build           # vinext build
npm run start           # vite preview on 127.0.0.1:3000 (server-PC check of the built output)
npm run serve:lan       # vite preview on 0.0.0.0:3000 — the production runtime (run it through the launcher)
npm run lint             # eslint . --ignore-pattern dist --ignore-pattern .next
npm test                 # npm run build, then node --test over an explicit list of tests/*.test.mjs
npm run db:generate      # drizzle-kit generate (writes drizzle/NNNN_*.sql from db/schema.ts)
npm run assistant:claude # local Claude CLI bridge for the in-app AI assistant (127.0.0.1:3130)
npm run resume:bridge    # local Claude CLI bridge for HR resume analysis (127.0.0.1:3120)
npm run assistant:bridge # legacy Codex CLI assistant bridge (127.0.0.1:3110), kept for rollback
```

`npm test` does **not** glob — it runs the test files listed by name in the `package.json` `test` script. A new `tests/*.test.mjs` file must be added to that list or `npm test` won't run it (`tests/removal-guards.test.mjs` fails when the list and the directory disagree).

Test files are plain `node --test` files, so run one directly, e.g. `node --test tests/erp-platform.test.mjs`. Most tests read source files as text and don't need a build. `tests/rendered-html.test.mjs` and `tests/bundle-exposure.test.mjs` need `npm run build` first. `tests/helpers/hr-api-harness.mjs` loads real route files through a TypeScript loader hook and runs them against an in-memory `node:sqlite` database standing in for D1. Use it for behavioral route tests (see `tests/hr-api-integration.test.mjs`).

## Stack

Next.js-shaped app router code (`app/`) served through **vinext** (Cloudflare's Next-compatible framework), written as a Cloudflare Worker with a D1 (SQLite) database and an R2 bucket (`HR_AUDIO`). `.openai/hosting.json` declares the D1/R2 binding names (`d1`, `r2`); `vite.config.ts` reads that file and simulates the bindings locally via `@cloudflare/vite-plugin`. `worker/index.ts` is the actual Worker entry point — it wraps vinext's app-router handler, adds security headers, and handles the `/_vinext/image` image-optimization route.

**How it actually runs.** The Cloudflare deployment was cancelled; the app runs on one office PC. From R3 the production runtime is **`vinext build` + `vite preview`** (`npm run serve:lan`, `0.0.0.0:3000`) in a separate operations folder (`C:\xdm\prod`, plan D18), started by [scripts/Start-XDNodeManagement.ps1](scripts/Start-XDNodeManagement.ps1): it refuses to start behind a `netsh` portproxy, builds when `dist/.build-rev` differs from `HEAD`, writes `dist/server/.dev.vars` with [scripts/write-dev-vars.mjs](scripts/write-dev-vars.mjs) (only the five allow-listed keys; preview ignores `.env.local`), then starts preview and the 3120/3130 bridges. The development folder uses `npm run dev` (`127.0.0.1:3100`). Don't use `vinext start` (no D1/R2 bindings) or `wrangler dev` (the local-peer plugin isn't loaded) as a runtime. The D1/R2 data lives in the serving folder's `.wrangler/state/` (Miniflare SQLite + blob files) — until the R3 cutover moves it, the development folder's copy is the live company database, not a disposable cache. Don't delete or reset it. Inspect only copies: `scripts/verify-state-snapshot.mjs` refuses to open the live directory. `scripts/restore-known-data.mjs` and `scripts/import-leave-ledger.mjs` go through the app API, logging in with [scripts/xdm-login.mjs](scripts/xdm-login.mjs) (`XDM_EMAIL`/`XDM_PASSWORD` or `--cookie`; it adds `Origin: <base>` to non-GET requests). Operations, cutover steps and smoke checks are in [docs/lan-operations-runbook.md](docs/lan-operations-runbook.md).

**LAN-exposure guards (R0, R3).** The dev server binding to `127.0.0.1` (not `0.0.0.0`), `X_LOCAL_EXPLORER = "false"` (the Miniflare explorer exposes an arbitrary-SQL API against D1), and `DEV_FS_DENY` in `vite.config.ts` (which must restate Vite's default deny patterns and anchor folder patterns to `PROJECT_ROOT`) are pinned by [tests/lan-exposure-guards.test.mjs](tests/lan-exposure-guards.test.mjs). From R3 the same test pins: [build/local-peer-vite-plugin.ts](build/local-peer-vite-plugin.ts) as the **first** plugin with `enforce: "pre"`, `cloudflare({ inspectorPort: false })`, no `allowedHosts` (Vite's host check is the only DNS-rebinding defence, so tell users the IP, not the PC name), `strictPort`, and the launcher/npm-script shape. The plugin strips any client-sent `x-xdm-peer` from `req.headers` and `req.rawHeaders` and restamps it from `req.socket.remoteAddress`; `peerOf()` in `app/auth-session.ts` trusts only that header (bootstrap and the D21 loopback login exemption depend on it). For non-loopback peers it returns 404 for `/cdn-cgi/*` and `/__debug*` and 403 for `/api/auth/bootstrap`, and it destroys every upgrade except loopback Vite HMR in dev. Its behaviour is tested in [tests/local-peer-plugin.test.mjs](tests/local-peer-plugin.test.mjs) (`build/**` is not linted). Don't loosen these without a plan change.

## Architecture

This is **XDnode management**, a single Korean-language internal tool for one company's 경영지원실 (management support team), not a generic starter. "XD NODE" is the company name and still appears in company-facing text (interview templates, the company profile, export file names); the product name is "XDnode management" and the package is `xdnode-management`. The D1 `database_id` / R2 `bucket_name` in `vite.config.ts` still carry the template's `site-creator-*` names on purpose: miniflare derives the state file names from them, so renaming them would silently open an empty database (pinned by `tests/removal-guards.test.mjs`).

**Frontend shell.** [app/page.tsx](app/page.tsx) is a small client component that is the whole app shell: it switches between the registry tabs (`hr`, `compensation`, `chat`, `general`, `audit`, `admin`) and mounts `HRWorkspace` ([app/hr-workspace.tsx](app/hr-workspace.tsx), ~4,900 lines, rendered in a shadow root styled by `public/hr-workspace.css`, with its screens in `hr-*-view.tsx` / `*-view.tsx`), `CompensationCalculator`, `ChatWorkspace`, `GeneralWorkspace`, `AuditLogWorkspace`, or `AdminAccountsWorkspace`. The messenger (R5) polls `/api/chat/poll` from the shell (`useChatPoll` in [app/chat-client.ts](app/chat-client.ts): 2 s on the chat tab, 15 s elsewhere) for the tab badge and `(N) XDnode management` title; server helpers are in [app/chat-server.ts](app/chat-server.ts), DDL in `app/chat-schema.ts`, and `app/api/chat/read-state` is the one mutating route with no audit row. The 총무 tab (`general`, [docs/02-design/features/general-affairs.design.md](docs/02-design/features/general-affairs.design.md)) keeps its tables in `app/ga-schema.ts` (`ga_*`, route-shared gate `ensureGaSchema`), pure date/alert/depreciation math in `app/ga-alerts.ts` and Excel sheet rules in `app/ga-import.ts`; its daily messenger digest (`POST /api/general/alerts`) is called session-less from the server PC by `scripts/Run-GaAlerts.ps1` (loopback + `X-XDM-Task`) and posts as the non-account author `system:ga`. Attachment type/size/header rules shared by chat and 총무 live in `app/attachment-rules.ts`. The 총무 registration forms can AI-fill fields from a PDF/image: the browser turns the file into page images + PDF text (`app/ga-extract-client.ts`), `POST /api/general/extract` forwards them to the resume bridge's `/extract` path (images passed on stdin via `--input-format stream-json`, tools still off), and `app/ga-extract.ts` keeps only whitelisted fields; nothing is saved until the user presses 저장. Navigation is client-side state (`useState`), not Next `Link`/route segments. `app/incentive/` is the one exception: a standalone routed page outside the SPA shell.

**API routes.** Each `app/api/<module>/<feature>/route.ts` is self-contained: it exports `GET`/`POST`/`PUT`/`DELETE`, and near-universally follows this pattern:
1. `ensureSchema()` — runs `CREATE TABLE IF NOT EXISTS` / index statements via `db.batch(...)`. There is no separate migration-apply step at runtime; the `drizzle/NNNN_*.sql` files under [drizzle/](drizzle/) are a historical record generated by `drizzle-kit generate`, but the actual runtime schema is created idempotently inline in each route file.
2. `authorizeErpRequest(db, module, action)` from [app/erp-platform.ts](app/erp-platform.ts) — resolves the caller's identity, employee record, and role, and checks `module:action` permission. Returns either `{ principal }` or `{ response }` (a ready-to-return 401/403 `Response`) — callers check `authorization.response` first.
3. Business logic via raw `db.prepare(...).bind(...).all()/.first()/.run()` (D1's native API), not the Drizzle query builder.
4. `writeErpAudit(db, { principal, module, action, entityType, entityId, before, after })` on every mutation, for the audit trail.

**Authorization model** ([app/erp-platform.ts](app/erp-platform.ts), [app/access-tabs.ts](app/access-tabs.ts)): the caller is the account behind the `xdm_session` cookie (`auth_accounts`/`auth_sessions`, [app/auth-session.ts](app/auth-session.ts)). An account has `is_admin` and per-tab grants in `tabs_json` (`hr`, `compensation`; each `none | view | edit`). `audit` and `admin` tabs are admin-only. `TAB_REGISTRY` in `app/access-tabs.ts` is the single list of tabs; `TabKey`, `ErpModule` and `MODULE_TAB` are derived from each entry's `modules`. `authorizeErpRequest(db, "<literal module>", action)` maps `read→view` and `write|approve|delete→edit`, and refuses modules outside the registry even for admins. Use `isHrManager(principal)` (admin or `hr=edit`) for manager-only branches, and use `linkedEmployeeId(principal)` for self/manager checks, because unlinked accounts use an `acct_…` id that is not an HR record. Route tests switch identity with the harness's `setAccess(tabs, opts)`.

**No approvals (direct apply).** The e-approval engine is gone (plan D2-개정). HR state changes that used to wait for sign-off (personnel actions, retirements, leave requests, payroll approval, performance finalization, workforce-plan approval, requisition opening) now apply immediately for a caller with the permission. The statement builders live in [app/hr-transitions.ts](app/hr-transitions.ts): pure functions returning `D1PreparedStatement[]`, guarded by `WHERE status IN (<from>, <legacy pending>)`; the route runs `db.batch` and returns 409 `CONFLICT` when `meta.changes` is 0. Rows left `SUBMITTED`/`PENDING` from the approval era are decided through the same buttons. The old `erp_approval_*`, finance and sales tables stay in the DB (never dropped, D4), but no code creates or reads them.

**How to add a tab** (FR-16, Design §10.7):
1. Add one entry to `TAB_REGISTRY` in [app/access-tabs.ts](app/access-tabs.ts) (fields `key`, `label`, `glyph`, `adminOnly`, `modules`, `apiPrefixes`, `shellClass`). `TabKey`, `ErpModule` and `MODULE_TAB` are derived; putting one module on two tabs throws at load.
2. Add one entry to `TAB_PANELS` in [app/page.tsx](app/page.tsx). There is no type-check step (the build only transpiles), so a missing panel still builds — `tests/shell-tabs.test.mjs` catches it by checking every registry key is in `TAB_PANELS`.
3. Create `app/api/<new module>/…/route.ts` that calls `authorizeErpRequest(db, "<new module>", …)` with a string-literal module before reading the body. Keep its schema in the route-local `ensureSchema`; don't touch the shared auth/chat DDL.

No permission data migration is needed (a key missing from `tabs_json` means `none`), the account screen's grant list is derived from the registry, and the existing `tab-permissions` source guard and `access-policy` registry checks cover the new tab automatically.

**Schema placement.** Auth, chat and operations DDL live only in `ensureErpPlatformSchema` (reached through the `platformSchemaReady` gate in [app/erp-platform.ts](app/erp-platform.ts)); route-local `ensureSchema` holds only that domain's tables. Add, never DROP.

**Harness rules** (Design §8.5). Route tests use `setAccess(tabs, { isAdmin, employeeId, mustChangePassword })`, `createAccount`, `login`, `setPeer` (default peer is the non-loopback `192.0.2.10`) and `setClock`; `callApi` returns `{ status, body, headers, setCookies, response }`. Server code imports `.ts` files by extensionless relative path only (no `@/`, directory index or `.tsx` imports), never uses `cookies()` or `'use server'`, and binds booleans as 1/0.

**Drizzle.** [db/schema.ts](db/schema.ts) and [db/index.ts](db/index.ts) exist (used by `npm run db:generate`) but are not imported anywhere under `app/` — nothing in the running app uses the Drizzle query builder or `getDb()`. Treat `db/schema.ts` as a migration-authoring surface only; actual reads/writes happen through raw SQL in route files as described above.

**Data files.** [app/hr-company-data.ts](app/hr-company-data.ts) embeds the real employee roster and pay seed — not synthetic fixtures — and is **server-only** (`import "server-only"`, so a client import fails the build). Client code imports the org/rank/title catalogs from `app/hr-company-catalogs.ts` and loads employees from `/api/hr/employee-records`; `tests/bundle-exposure.test.mjs` checks that no seed name, phone, email or salary reaches `dist/client`. Treat edits as data-accuracy-sensitive. The finance data files were removed from the tree (kept only in tag `erp-final-20260923` and an archive outside the repo).

**Local AI bridges.** The Worker can't spawn processes, so AI features call small Node HTTP servers in `scripts/` that wrap the `claude` CLI and run on the desktop. [app/api/assistant/route.ts](app/api/assistant/route.ts) proxies to `CLAUDE_ASSISTANT_BRIDGE_URL`, which defaults to `http://127.0.0.1:3130` (`scripts/claude-assistant-bridge.mjs`). The browser never calls the bridge directly, so other devices on the network can still use the assistant. The bridge validates model output against `scripts/codex-assistant-response-schema.json`, because `proposedActions` are change proposals the UI can apply to real ERP records. [app/api/hr/resume-analysis/route.ts](app/api/hr/resume-analysis/route.ts) calls `CLAUDE_BRIDGE_URL`, which defaults to `:3120` (`scripts/claude-resume-bridge.mjs`, an OpenAI-compatible `/chat/completions` shim). The bridges bind to localhost, cap request size, and handle one request at a time.

**Docs.** [docs/](docs/) contains one `*-plan.md` per HR/platform feature area describing intended behavior — check the relevant plan doc before changing a workspace's business rules. The finance, sales, data and master-impact plans are in `docs/archive/` for reference only.

**In-flight restructuring (`xdnode-management`).** [docs/00-pm/xdnode-management.prd.md](docs/00-pm/xdnode-management.prd.md), [docs/01-plan/features/xdnode-management.plan.md](docs/01-plan/features/xdnode-management.plan.md), and [docs/02-design/features/xdnode-management.design.md](docs/02-design/features/xdnode-management.design.md) describe a plan to rename the product "XDnode management" and turn it into a tool for the 경영지원실 (management support team). Its phases are real accounts/sessions with per-role tab visibility, then team chat, then a link to a quotation tool. Release R1 has **removed the finance and sales modules** and, per D2-개정, the approval engine as well. The audit trail (`writeErpAudit`) stays, and `app/incentive/` stays but no longer uses sales data. Git tag `erp-final-20260923` marks the last state that still contains finance, sales, and approvals. Before changing platform or shell code, check the plan/design docs for the current phase and decisions (numbered `D1`, `D2`, …, which code comments and tests reference).

## Conventions

- UI text and most identifiers/comments are Korean; currency is KRW (`Intl.NumberFormat("ko-KR", { style: "currency", currency: "KRW" })` / `formatWon` helpers). Keep new user-facing strings in Korean to match the rest of the app.
- `tests/*.test.mjs` mostly assert (via regex) that specific source files contain specific guardrails — e.g. that every sensitive API route calls both `authorizeErpRequest` and `writeErpAudit`, or that a specific SQL/UI string exists — rather than executing the app end-to-end. `tests/erp-platform.test.mjs` scans every `app/api/**/route.ts` and fails if a mutating one lacks either call; `tests/removal-guards.test.mjs` keeps the removed finance/sales/approval/data paths from coming back.
- The repo root also holds a large number of untracked, non-source artifacts (`xdnode-erp-v*.tar.gz` snapshots, `council-report-*` / `council-transcript-*` files, `deliverables/`, `analysis/`, `tools/`, root-level `*.py` workbook-analysis scripts, `.bkit/`, `work_incentive/`, `tmp/`, `tmp_modelb_refresh/`, `.codex*-analysis/`, etc.) from prior working sessions. These are not part of the application and shouldn't be treated as architecture references or added to as a side effect of unrelated work.
