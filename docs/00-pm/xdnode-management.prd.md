# PRD: XDnode management — 경영지원실 종합 툴

| 항목 | 내용 |
|------|------|
| Feature | `xdnode-management` |
| 단계 | PM (pre-Plan) |
| 작성일 | 2026-09-23 |
| 대상 사용자 | 경영지원실 5~6명 (사내 전용) |
| 배포 형태 | 사무실 PC 1대를 서버로 사용, 사내 LAN 접속 |
| 다음 단계 | `/pdca plan xdnode-management` |

> 이 문서는 시장 출시용 제품이 아닌 **5~6명이 쓰는 사내 도구**의 PRD다. 시장 규모·경쟁사·GTM 같은 항목은 형식상 짧게만 다루고, 깊이는 (1) 사용자 5~6명의 실제 업무(JTBD), (2) 범위 결정, (3) 리스크, (4) 사용자 스토리와 테스트 시나리오에 둔다.

---

## 0. Executive Summary

| 관점 | 요약 |
|------|------|
| 문제 | 현재 "XD NODE ERP"는 재무회계·영업·HR·임금계산을 한 화면에 묶은 단일 사용자용 앱이다. 접속자 전원이 `LOCAL_ERP_USER_EMAIL` 한 사람으로 취급되어 **누가 무엇을 했는지 구분이 안 되고, 급여·인사 데이터가 접속 가능한 모든 사람에게 노출**된다. 팀 대화는 도구 밖(카카오톡 등)에 흩어져 있다. |
| 해결 | 제품을 **XDnode management**로 재명명하고 경영지원실 종합 툴로 재편한다. (0) 실제 계정·세션·역할 기반 탭 노출 제어를 먼저 만들고, (1) Slack형 팀 채팅(채널·DM·스레드·파일·멘션·검색)을 붙이고, (2) 별도 진행 중인 견적서 자동화 툴을 연결한다. 동시에 **재무회계·영업 모듈은 완전히 제거**한다. |
| 기능/UX 효과 | 로그인 후 자기 권한에 맞는 탭만 보인다(없는 탭은 존재조차 안 보임). 같은 화면에서 인사·급여 업무와 팀 대화를 오간다. 사용하지 않는 재무·영업 탭 40여 개 컴포넌트가 사라져 화면과 코드가 가벼워진다. |
| 핵심 가치 | 경영지원실 5~6명이 **한 도구, 한 계정 체계, 한 서버 PC**에서 안전하게 소통하고 일한다. 급여 데이터는 권한 있는 사람만 본다. |

**#1 선행 조건**: 계정(로그인·세션·사용자별 신원)이 없으면 채팅도(발신자 구분 불가), 탭 권한도(누구인지 모름) 성립하지 않는다. 따라서 **Phase 0 = 계정 체계**가 채팅보다 먼저다.

## 1. 배경과 현재 상태 (코드에서 확인한 사실)

| 영역 | 현재 상태 | 이번 과제에 미치는 의미 |
|------|-----------|--------------------------|
| 스택 | vinext(Next 호환) + Cloudflare Worker 형태, D1(SQLite)·R2. 사무실 PC에서는 `scripts/Start-XDNodeERP.ps1`가 `npm run dev -- --port 3000 --hostname 0.0.0.0`로 **개발 서버**를 띄우고, 보조 브리지 3110/3120/3130을 함께 올린다. | 실제 Cloudflare 배포가 아니라 **로컬 시뮬레이션(miniflare)** 위에서 D1/R2가 동작한다. 데이터는 `.wrangler/state` 아래 파일(SQLite)에 저장된다. 백업·가용성·실시간 통신 방식이 전부 이 전제에 묶인다. |

## 2. Discovery — 기회 구조 (Opportunity Solution Tree, 요약)

**목표 성과(Outcome)**: 경영지원실 5~6명이 외부 메신저 없이, 각자 권한에 맞는 화면만 보면서, 하나의 사내 도구에서 소통하고 업무를 끝낸다.

| # | 기회(Opportunity) | 근거 | 해결안(Solution) | 검증 실험 |
|---|-------------------|------|-------------------|-----------|
| O1 | 접속자가 모두 같은 사람으로 취급된다 → 감사 로그가 무의미하고, 급여 데이터 노출 | `chatgpt-auth.ts` fallback, 서버 PC 공용 접속 | 로컬 계정(이메일+비밀번호) + 서버측 세션 + `erp_user_access` 연결 | 2명이 동시에 로그인해 감사 로그 `actor`가 다르게 찍히는지 |
| O2 | 권한 없는 탭이 보여 실수·혼란·정보 노출 | 탭이 `page.tsx`에 하드코딩 | 서버가 `/api/me`로 "보이는 탭 + 권한"을 내려주고 셸이 거른다. API 가드 병행 | VIEWER로 로그인 시 급여 탭 미표시 + 급여 API 직접 호출 403 |
| O3 | 팀 대화가 도구 밖에 흩어져 업무 맥락과 분리 | 사용자 요구 | Slack형 채팅 MVP(채널·DM·스레드·파일·멘션·검색·미확인 배지) | 1주간 카카오톡 대신 사용 후 "돌아가고 싶은가" 인터뷰 |
| O4 | 재무·영업 모듈이 경영지원실 업무와 무관한데 화면·코드·리스크를 키움 | 사용자 결정("완전히 덜어낼 예정") | 재무·영업 제거 워크스트림(§6 R) | 제거 후 `npm test`·HR 시나리오 회귀 통과 |
| O5 | 견적서 작업이 별도 도구에서 이뤄져 이중 입력 | 사용자 언급(별도 진행 중) | Phase 2에서 연결(방식 미정: 병합/임베드/API) | Phase 2 착수 전 결정 |

**핵심 가정(영향 × 위험 상위)**
1. 5~6명 규모에서 **폴링 기반** 채팅도 "실시간"으로 충분히 느껴진다. (위험: 체감 지연) → MVP에서 2~3초 폴링으로 측정.
2. 사무실 PC 1대가 업무 시간 내 계속 켜져 있고 LAN 접근이 열려 있다. (위험: 방화벽·절전·재부팅) → 시작 스크립트 자동 실행 + 헬스체크.
3. 역할 6종 대신 "역할 기반 탭 + 사용자별 예외"로 5~6명의 권한을 충분히 표현할 수 있다. → 실제 인원 매핑 표로 검증(§13 Q3).
4. 재무·영업을 걷어내도 승인·감사·HR이 깨지지 않는다. (위험: 공유 코드 의존) → 의존 그래프 확인 후 제거.

## 3. 사용자 — 페르소나 3종과 JTBD

전원 경영지원실 소속, 같은 사무실, 같은 LAN. 시장 세그먼트가 아니라 **실제 5~6명의 역할 유형**이다.

### P1. 경영지원실장 (관리자, 1명)
- 역할: 인사·급여·총무 총괄. 계정 발급과 권한 부여 담당(가정).
- JTBD: "새 팀원이 오면 **5분 안에 계정을 만들고 볼 수 있는 탭을 정해 주고**, 급여 탭은 나와 급여 담당만 보이게 하고 싶다."
- 고통: 지금은 누가 뭘 봤는지 모른다. 권한 변경은 코드 수정이다.
- 성공 기준: 계정 관리 화면에서 사용자 추가·역할/탭 지정·비활성화가 된다.

### P2. HR·급여 담당자 (1~2명)
- 역할: 직원 기록, 임금 계산, 퇴직금, 채용 요청 처리.
- JTBD: "급여 계산하다 생긴 질문을 **같은 화면에서 실장에게 DM**으로 묻고, 엑셀 파일을 바로 첨부하고 싶다."
- 고통: 카카오톡 ↔ ERP 화면 전환, 파일 이중 전송.
- 성공 기준: HR 탭 + 임금계산 탭 + 채팅이 한 로그인으로 보인다.

### P3. 총무·일반 스태프 (2~3명, 향후 견적 담당 포함)
- 역할: 총무, 문서, 향후 견적서 작성.
- JTBD: "팀 채널에서 공지·대화를 하고, **내 일에 필요한 탭만** 보이면 된다. 급여는 볼 수도 없고 보이지도 않아야 한다."
- 고통: 관련 없는 탭이 잔뜩 보이면 실수하거나 눌러보게 된다.
- 성공 기준: 로그인 후 채팅 + 허용된 탭만. 견적 탭은 Phase 2에서 추가.

### 대표 사용자 여정 (P2, Phase 1 이후)
1. 사무실 PC로 `http://<서버IP>:3000` 접속 → 로그인 화면
2. 이메일·비밀번호 입력 → 세션 쿠키 발급 → 자기 탭(HR, 임금계산, 채팅)만 보이는 셸
3. `#경영지원` 채널 미확인 배지 확인 → 공지 읽음
4. 임금계산 탭에서 계산 → 이상치 발견 → 실장 DM에 화면 캡처 첨부 → 스레드로 답변
5. 로그아웃(또는 세션 만료). 감사 로그에는 P2 본인의 이메일로 기록

### SWOT (요점만)
- S: 이미 작동하는 HR·급여·승인·감사 기반. 서버측 `module:action` 가드 존재.
- W: 인증 부재, 개발 서버로 운영, 단일 PC, 1,560줄 SPA 셸에 모듈이 하드코딩.
- O: 재무·영업 제거로 코드·리스크 절반 이상 감소. 채팅이 붙으면 승인 알림 등 연계 여지.
- T: "완전한 Slack 클론" 범위 폭발, 서버 PC 장애 시 전원 업무 중단, 브리지 origin 고정으로 다른 PC에서 AI 어시스턴트 불가.

## 5. 대안 분석 (Buy vs Build) — 형식상 짧게

시장 규모(TAM/SAM/SOM)는 이 프로젝트에 **의미가 없다**(사용자 6명, 매출 0). 대신 "만들지 말고 사서 쓸 수 있나"만 본다.

| 대안 | 장점 | 단점(이 팀 기준) | 판단 |
|------|------|------------------|------|
| Slack (무료/유료) | 완성도 최고 | 데이터 외부 저장, 무료 플랜 90일 제한, ERP와 분리 | 대체 불가 — 사용자가 "ERP 안 채팅"을 원함 |
| Microsoft Teams | M365 있으면 무료 | 무겁고 ERP와 분리 | 동일 |
| KakaoWork / Jandi | 국내형, 한국어 | 외부 SaaS, 권한 모델이 ERP와 무관 | 동일 |
| Mattermost / Rocket.Chat 셀프호스트 | 사내 데이터 유지 | 별도 서버 프로세스·DB, 계정 이중 관리 | 계정 통합 없으면 탭 권한 요구를 못 채움 |
| **자체 구현(이 PRD)** | 계정·권한·업무 화면 통합, 데이터 사내 유지 | 개발 부담, 운영 책임 | **채택**, 단 범위를 MVP로 자름 |

배틀카드는 없다. 경쟁이 아니라 "왜 직접 만드는가"의 답은 하나다: **계정·권한·업무 화면을 하나로 묶어야 하기 때문**.

## 6. 범위 (Scope)

### Phase 0 — 기반: 리네임 + 계정 + 탭 권한 (채팅보다 먼저)
**In**
- 제품명 "XDnode management"로 표시 리네임: `app/layout.tsx` 제목/OG, `app/page.tsx` 브랜드 2곳, "XD NODE" 문자열 13개 파일, 시작 스크립트 표시 문구. (패키지명·폴더명 변경 여부는 §13 Q6)
- 로컬 계정: 이메일 + 비밀번호(해시 저장), 로그인/로그아웃 화면, 서버측 세션(D1 테이블 + HttpOnly 쿠키), 세션 만료.
- 기존 `LOCAL_ERP_USER_EMAIL` fallback은 **"계정이 0개일 때 최초 관리자 부트스트랩" 용도로만** 남기고, 계정이 1개 이상 생기면 비활성화.
- 계정 관리 화면(관리자): 사용자 추가/비활성화, 비밀번호 초기화, 역할 지정, 탭 노출 지정.
- 탭 노출: 서버 `/api/me`가 `{ user, roles, visibleTabs, permissions }` 반환 → `page.tsx` 모듈 목록을 이것으로 필터. 허용되지 않은 탭은 **DOM에 렌더하지 않음**. URL/상태로 강제 진입 시 "권한 없음" 화면.
- 서버 가드 유지: 모든 API는 계속 `authorizeErpRequest`. 새 모듈 `chat`, (Phase 2) `quote` 권한 문자열 추가. `FINANCE_ADMIN`, `SALES_ADMIN` 역할 제거(§6 R).
- 감사 로그 `actor`가 실제 로그인 사용자로 기록되는지 확인.

**Out**: SSO, 2FA, 비밀번호 정책 고도화, 외부(사외) 접속.

### Phase 1 — Slack형 팀 채팅 MVP
"완전한 Slack 클론"을 그대로 만들면 수개월이 걸린다. 5~6명에게 **필요한 최소 컷**을 권고하고, 확정은 §13 Q1로 넘긴다.

| 기능 | MVP 권고 | 비고 |
|------|----------|------|
| 공개 채널 | **In** | 생성·참여·목록. 비공개 채널은 In(권한상 필요) |
| DM (1:1, 소그룹) | **In** | |
| 스레드(답글) | **In** | 1단계 깊이 |

- 실시간: MVP는 **2~3초 짧은 폴링**(또는 long-polling)으로 시작. 서버가 `since` 커서로 증분 반환. SSE/WebSocket(Durable Objects 시뮬)은 체감 지연이 문제일 때 승격(§13 Q2).
- 저장: 메시지·채널·멤버·읽음 위치를 **동일 D1**에 저장(별도 DB를 두면 백업·계정 연결이 이중화됨). 확정은 Q2.

| D8 | **견적서 자동화 툴은 이번 범위에서 제외한다.** 툴이 아직 제작 중이며, 안정화된 뒤 사용자가 공유한다. 이번에는 새 탭을 쉽게 추가할 수 있는 탭·권한 구조만 만들어 둔다(FR-13). | Q4 답변 |
| D9 | **`app/sales-pricing.ts` 견적 로직은 승계하지 않는다.** 노트 추출 없이 영업 코드와 함께 삭제한다(아카이브 태그에는 남음). | Q7 답변 "아니" |
| D10 | **접속은 사무실 내부망에서만 한다.** 외부 원격 접속, HTTPS, VPN은 범위 밖이다. 다른 PC는 LAN으로 서버 PC에 접속한다. 고정 LAN IP 지정과 Windows 방화벽 인바운드 3000 허용이 필요하다. AI 어시스턴트 브리지의 origin 허용 목록은 서버 LAN 주소를 포함하도록 고친다(NFR-06). | Q5 답변 "사무실 내부에서만. 내부망으로 접속" |
| D11 | **리네임은 전부 한다.** 대상: 표시명(UI·제목·문서), `package.json` 이름, 시작 스크립트 이름, 저장소 이름, 프로젝트 폴더명(`XDNODE`). **폴더명·저장소명 변경은 맨 마지막에** 한다. 앱이 멈춘 상태에서 이 PC의 작업 세션을 모두 닫고 해야 한다. 폴더 경로를 참조하는 곳(시작 스크립트 바로가기, 작업 스케줄러, `XD_NODE_PROJECT_PATH`, Claude Code 프로젝트 메모리 경로)을 함께 옮긴다. | Q6 답변 "전부 변경". 폴더 이동은 실행 중인 서버·세션 경로를 깨므로 순서를 고정 |

## 8. 아키텍처 제약과 결정 지점 (Plan/Design 단계로 넘길 항목)

1. **런타임**: 로컬 miniflare 위 vinext. Durable Objects·WebSocket은 로컬 시뮬에서도 동작하지만, 개발 서버 재시작 시 연결이 끊긴다. → MVP 폴링, 승격 시 SSE 우선 검토.
2. **영속성**: D1 = `.wrangler/state/v3/d1/**.sqlite`. 파일 복사로 백업 가능. `vinext dev`와 `vinext start`가 같은 상태 디렉토리를 쓰는지 확인 필요.
3. **세션 저장**: D1 `erp_sessions` 테이블(권고). 쿠키에는 세션 ID만.
4. **탭 모델**: `visibleTabs`는 역할 기본값 + 사용자별 override(권고, Q3에서 확정). 서버 한 곳에서 계산해 UI와 API가 같은 소스를 본다.
5. **모듈 확장**: 채팅·견적은 기존 `app/api/<module>/<feature>/route.ts` 패턴(`ensureSchema` → `authorizeErpRequest` → raw D1 → `writeErpAudit`) 그대로 따른다.
6. **접속 경로**: 서버 IP가 DHCP로 바뀌면 URL이 바뀐다 → 고정 IP 또는 hosts 이름 권고. Vite dev server의 `allowedHosts`는 IP 접속은 기본 허용, 호스트명 접속은 설정 필요.

> Q1→D5, Q2→D6, Q3→D7, Q4→D8, Q5→D10, Q6→D11, Q7→D9, Q8→D2-개정·D2-a·D2-b·D2-c. 아래 표는 기록용으로 남긴다. 본문 중 이 결정과 어긋나는 서술(예: "승인 엔진 유지", "`sales-pricing.ts` 노트 추출", "역할 기본 + 사용자 예외")은 §6.1·§6.2가 우선한다.

| # | 질문 | 왜 지금 필요한가 |
|---|------|------------------|
| Q1 | "완전히 Slack 클론"의 1차 범위는 어디까지인가? 채널·DM·스레드·반응·파일·멘션/알림·검색·미확인 배지·presence·수정/삭제 중 무엇이 1차 필수인가? (§6 Phase 1의 MVP 권고안에 동의하는가) | 개발 기간이 2배 이상 갈린다 |
| Q2 | 실시간 방식: 폴링 / SSE / WebSocket(Durable Objects 시뮬) 중 어느 것을 목표로 하는가? 메시지를 기존 D1과 같은 DB에 저장하는가? | 로컬 vinext dev 위 구현 난이도와 백업 단위가 달라진다 |
| Q3 | 계정과 탭 권한은 **누가** 관리하는가(실장? 개발자?). 탭 노출은 **역할별**인가 **사용자별**인가(혹은 역할 기본 + 사용자 예외)? 기존 6역할 모델을 대체하는가 확장하는가? | 계정 관리 화면과 권한 모델 설계의 출발점 |
| Q4 | 견적서 자동화 툴은 어느 저장소/스택에 있고, 어떻게 붙이는가(코드 병합 / iframe 임베드 / API 연동 / 별도 탭 링크)? | 지금 탭·권한·인증 모델을 어떤 형태로 열어 둘지 결정 |

| Q6 | 리네임은 **표시명만**인가, `package.json` 이름·저장소 이름·폴더명(`XDNODE`)·시작 스크립트 파일명까지인가? | 리네임 작업 범위와 다른 도구(스크립트 경로) 영향 |
| Q7 | (Phase 2 입력) `app/sales-pricing.ts`에서 추출한 견적 가격 검토 로직 노트를 견적서 자동화 툴이 **실제로 승계**하는가, 아니면 툴이 자체 가격 로직을 가지는가? | 노트 추출 자체는 D3로 결정됨. 승계 여부만 견적 툴 담당자 확인 |
| Q8 | **권장 조정 — 사용자 확인 필요**: 승인 엔진·감사 기록 인프라는 HR 의존으로 유지한다(§6.1 D2). 그 위의 **HR용 승인 수신함 화면**과 **감사 로그 조회 화면**도 남기는가? 권고: 두 화면을 HR 전용 슬림 버전으로 유지(없으면 급여·휴가·채용 승인 요청을 처리할 UI가 사라진다) | 제거 범위 확정. 사용자의 "빼자"가 화면까지 포함하는지 명확히 할 것 |
