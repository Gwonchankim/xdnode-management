# general-affairs Planning Document

> **Summary**: XDnode management에 총무 탭을 더한다. 자산 4종(지급 장비·비품/소모품·계약/구독·고정자산), 회사 서류 원본 보관과 만료 관리, 법인인감·서류 반출 대장을 한 사이클에 만든다. 만료 알림은 탭 배지와 메신저 채널 글로 한다.

> **Project**: XDnode management

## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | 회사 자산과 서류가 엑셀 일부, 담당자 기억, 캐비닛에 흩어져 있다. 누가 어떤 노트북을 쓰는지, 도메인·보험·라이선스가 언제 끝나는지, 법인인감이 지금 누구 손에 있는지를 한곳에서 볼 수 없다. 만료를 놓치면 서비스 중단이나 과태료로 이어진다. 퇴직 체크리스트의 '회사 자산 반납'은 체크박스뿐이라 무엇을 돌려받아야 하는지 모른다. |
| **Solution** | 총무 탭(`general`)을 탭 레지스트리에 더한다. 장부는 네 개다. ① 자산 대장: 유형 4종, 지급·반납·이동·폐기 이력, 고정자산은 정액법 월할 감가상각. ② 회사 서류 대장: 원본 위치, 스캔본 첨부, 만료일. ③ 인감·서류 반출 대장: 반출·반납 기록. ④ 만료 알림: D-30·D-7·당일·경과 배지와 메신저 '총무' 채널 자동 글. 엑셀 양식으로 한 번에 가져오기를 제공한다. 퇴직 정산 화면에는 그 직원의 미반납 자산 목록을 보여 준다. |
| **Function/UX Effect** | 총무 권한자는 한 화면에서 만료 예정, 반출 중인 인감, 직원별 지급 장비를 본다. 직원이 퇴직하면 돌려받을 장비 목록이 자동으로 나온다. 만료가 가까워지면 탭 배지와 메신저로 알려서 놓치지 않는다. |
| **Core Value** | 회사 자산과 법적 서류의 현황, 책임자, 기한을 한곳에서 추적한다. 모든 변경은 감사 로그에 사람 이름으로 남는다. |

## Context Anchor

| Key | Value |
|-----|-------|
| **WHY** | 자산·서류·인감의 현황, 책임자, 만료일이 흩어져 있어 분실·만료를 놓친다. 퇴직 때 회수할 자산을 알 수 없다 |
| **WHO** | 경영지원실 총무 담당(편집), 실장·대표(보기), 관리자(전체). 일반 직원은 이 탭을 쓰지 않는다 |
| **RISK** | 인감·인증서 파일은 민감하다(스캔본 유출). 만료 알림이 시끄러우면 무시된다. 엑셀 가져오기에서 데이터가 틀어질 수 있다. 감가상각은 재무 전표와 섞이면 D2와 충돌한다 |
| **SUCCESS** | 기존 엑셀을 가져와 장부가 채워진다. D-30 안의 만료 항목이 탭 배지와 메신저에 같은 날 나온다. 반출 중인 인감이 첫 화면에 보인다. 퇴직 정산 화면에 미반납 자산이 뜬다. 권한 없는 계정은 탭과 API 모두 막힌다 |
| **SCOPE** | 한 사이클·한 릴리스(GA1)다. 새 탭 1개, 라우트 5~6개, 테이블 7~8개. 기존 HR·메신저 스키마는 추가만 한다 |

## 1. Overview

### 1.1 Purpose
경영지원실이 회사 자산, 법적 서류, 인감을 한 도구에서 관리하게 한다. 누가 가졌는지, 어디에 있는지, 언제 끝나는지를 추적한다.

### 1.2 Background
- D24(2026-09-28)에서 총무 탭을 메신저(R5) 다음 별도 사이클로 정했다. 범위는 자산 4종과 회사 서류(보관·만료·인감·반출 대장)다. 직원 증명서 발급은 요청하지 않았다.
- 재무 모듈의 고정자산 코드는 R1에서 지웠다. 보관 태그 `erp-final-20260923`에 남아 있다.
  - `app/api/finance/fixed-assets/route.ts` 340줄, `app/fixed-assets-workspace.tsx` 163줄, `app/fixed-asset-calculation.mjs` 30줄(정액법만)
  - 기존 테이블 `finance_fixed_assets`·`finance_asset_depreciation_schedules`·`finance_asset_events`는 데이터 0건으로 DB에 남아 있다(D4).
  - D24대로 이 코드를 가져와 총무 장부로 고쳐 쓴다. 재무 계정과목·전표 컬럼은 쓰지 않는다. 옛 `finance_*` 테이블은 읽지도 쓰지도 않고, 새 `ga_*` 테이블을 만든다.
- 퇴직 정산에는 이미 `assets_returned` 체크(`app/api/hr/operations/route.ts:67`)가 있다. 퇴직 체크리스트에는 '노트북·출입증 등 회사 자산 반납' 항목(`app/hr-workspace.tsx:859`)이 있다.
- 탭은 레지스트리 1항목, `TAB_PANELS` 1항목, 새 라우트만으로 추가된다(FR-16). 권한 데이터 이전은 필요 없다.
- 엑셀 라이브러리 `read-excel-file`·`write-excel-file`은 이미 의존성에 있다.

## 2. Scope

### 2.1 In Scope (릴리스 GA1, 한 번에 배포)

**A. 총무 탭과 권한**
- [x] 레지스트리 항목 `{ key: "general", label: "총무", modules: ["general"], apiPrefixes: ["/api/general/"] }`. 부여 수준은 none·view·edit다. 관리자는 전부 edit다. — `app/access-tabs.ts:11`, `TAB_PANELS.general`(`app/page.tsx:57`), ga-api #1·#16, tab-permissions·access-policy·shell-tabs 통과(2026-10-02)
- [x] 첫 화면 '현황' — `GET /api/general/overview`(alerts·openCheckouts·overdueCheckouts·summary(유형별 수량·장부가)·holders·lowStock), 화면 `OverviewView`
  - 만료 임박 목록(경과·당일·D-7·D-30)
  - 반출 중인 인감·서류와 반납 예정일 지난 건
  - 자산 유형별 수량과 장부가액 합계
  - 직원별 지급 장비 수

**B. 자산 대장** (유형 4종, 한 테이블 + 유형별 필드)
- [x] 공통 필드: 자산번호(자동 `GA-유형-연도-일련`, 수정 가능, UNIQUE), 이름, 유형, 분류, 상태, 위치, 담당자·사용자(직원), 취득일, 취득가, 공급처, 메모, 사진·증빙 첨부 — `ga_assets`(`app/ga-schema.ts`, 부분 UNIQUE `idx_ga_assets_no`), `nextAssetNo`, 첨부 `ga/ASSET/…`, ga-api #2·#4·#12
- [x] **지급 장비**(노트북·모니터·휴대폰·출입증 등) — ASSIGN·RETURN·MOVE 조건부 UPDATE, 같은 장비 재지급 409(ga-api #2)
  - 시리얼, 모델
  - 지급·반납·이동 이력. 현재 사용자는 하나다
- [x] **비품·소모품** — STOCK_IN/OUT(음수 400, 경쟁 409, ga-api #3), LOW_STOCK 현황 표시. 위치별 수량은 위치마다 행을 따로 두는 방식이다(Design GD-2, 한 행에 수량 1개)
  - 위치별 수량, 단위, 재고 기준(최소 수량)
  - 입고·출고 기록. 최소 수량보다 적으면 현황에 표시한다
- [x] **계약·구독**(소프트웨어 라이선스·도메인·호스팅·리스·보험·유지보수) — 필드 전부 `ga_assets`, RENEW·END, 자동 갱신은 알림 기본 끔(ga-api #8)
  - 계약처, 계약번호, 시작일, 만료일, 자동 갱신 여부, 갱신 비용, 결제 주기, 담당자
  - 만료 알림 대상이다
- [x] **고정자산**(회계상) — `depreciationSchedule`(`app/ga-alerts.ts`, 저장 안 함), DISPOSE 뒤 상각 정지(ga-api #5). 기초 누계가 있는 자산의 '월 상각액' 표시 오류는 2026-10-02 고쳤다([분석 문서](../../03-analysis/general-affairs.analysis.md) §2)
  - 내용연수(월), 잔존가치, 기초 상각누계와 기준일
  - **정액법 월할** 감가상각표(자동 계산, 저장하지 않고 계산), 처분일, 처분가
  - 재무 전표·계정과목과는 연결하지 않는다(D24·D2)
- [x] 이력(자산 이벤트): 취득, 지급, 반납, 이동, 수량 입고·출고, 수리, 처분·폐기. 각 이력에 사유를 남기고 감사 로그에 기록한다 — `ga_asset_events`(12종), 경쟁에서 진 요청은 이력 없음(`WHERE changes() > 0`), `GA_ASSET_<action>` 감사
- [x] 한 자산이 지급 장비이면서 고정자산일 수 있다(예: 고가 노트북). 이 경우 고정자산 필드를 선택 입력으로 둔다 — `assetFields`: EQUIPMENT 도 내용연수·잔존가치·기초누계를 선택 입력으로 받는다

**C. 회사 서류 대장**
- [x] 종류: 사업자등록증, 법인 등기부등본, 법인인감증명서, 사용인감계, 공동인증서·전자세금계산서 인증서, 인허가증, **기업 간 계약서**, 기타 — `ga_documents.kind` CHECK 8종
- [x] **기업 간 계약서**(GA-D2) — `kind='B2B_CONTRACT'` 필드, 자동 연장이면 해지 통보 기한만 알림(ga-api #8). '원본 보관 위치'는 GA-D6으로 입력에서 뺐다(대체됨): 물품공급 계약서, 파트너(대리점·협력) 계약서, 용역 계약서, 비밀유지 계약서, 기타
  - 필드: 계약 종류, 상대방(회사명), 계약일, 계약 시작일·종료일, 계약 금액(선택), 자동 연장 여부, 해지 통보 기한(종료일 N일 전), 원본 보관 위치, 관리 책임자, 스캔본
  - 알림 대상은 종료일과 해지 통보 기한이다. 자동 연장 계약은 해지 통보 기한만 알린다(연장을 원하지 않으면 그 전에 통보해야 하므로)
  - 계약·구독 자산(우리가 비용을 내는 서비스, B의 3번째 유형)과 구분한다. 기업 간 계약서는 법적 문서로서 원본·스캔본 관리가 목적이다
- [x] 필드: 발급기관, 발급일, 유효기간·만료일(선택), 원본 보관 위치(예: 캐비닛 A-2), 관리 책임자, 스캔본 첨부(PDF·이미지), 메모 — `documentFields`, 첨부 `ga/DOCUMENT/…`. '원본 보관 위치'는 GA-D6으로 대체됨(열은 남고 수정 때 기존 값 유지, ga-api GA-D6)
- [ ] 등기부등본·인감증명서처럼 제출용으로 새로 떼는 서류에는 '발급일 기준 N개월 유효' 안내 필드를 둔다. 기본값은 3개월이다 — **부분**: `validity_months` 필드와 만료 계산(`documentExpiry`)은 있으나 기본값 3이 들어가지 않는다(빈 칸 = 0)
- [x] 인증서는 파일 자체(비밀키 파일)를 올리지 않는다. 보관 위치와 만료일만 기록한다(§5 R-GA2) — `app/attachment-rules.ts` 확장자 표에 pfx·p12 등이 없어 415(ga-api #12)

**D. 인감·서류 반출 대장**
- [x] 대상: 법인인감, 사용인감, 회사 서류 원본(C의 항목), 기타 물품 — `ga_custody_items`(CORP_SEAL·USAGE_SEAL·OTHER) + `ga_checkouts.target_type` ITEM/DOCUMENT
- [x] 반출 기록: 반출자(직원), 반출 일시, 용도·제출처, 반납 예정일, 기록한 사람 — `POST /api/general/custody` CHECKOUT(반출일은 날짜 단위, `recorded_by`)

- [x] 같은 대상은 동시에 한 번만 반출할 수 있다(반출 중이면 409) — 부분 UNIQUE `idx_ga_checkouts_open`, ga-api #6, 반출 중 서류 삭제 409(#7)

- [x] 대상: 계약·구독 만료일, 회사 서류 만료일, 반출 반납 예정일, 비품 최소 수량 미달 — `collectAlerts`(`app/ga-alerts.ts`)
- [x] 구간: 경과, 당일, D-7, D-30. 항목마다 알림 끄기(예: 자동 갱신 계약)를 둔다 — `bucketOf`, 자산·서류 `alert_off`, KST 날짜 경계(ga-api #8)

- [x] 메신저 알림: 하루 한 번, 비공개 '총무' 채널에 시스템 글로 요약한다(새로 D-30·D-7·당일·경과 구간에 들어온 항목만) — `app/ga-alert-run.ts`(`ch_ga_alerts`, `system:ga`, `ga_alert_runs` 멱등, 멤버 동기화), ga-api #9~#11. 운영: `XDnodeManagement-Alerts` 09:00 + Start 후 따라잡기, 로그 `ga-alerts:` 매일 1회 실행(2026-10-01·10-02, members=2)

  - 실행 주기와 방식은 Design에서 정한다(후보: 03:00 백업 재기동 뒤 루프백 전용 호출)

**F. 엑셀 가져오기·내보내기**
- [x] 열 구성은 양식마다 이 기획이 정한다(GA-D1, 기존 파일에 맞추지 않는다). 열 정의는 Design에 둔다. 기존 엑셀은 사용자가 양식에 옮겨 붙인다 — `GA_SHEETS`(`app/ga-import.ts`). 회사서류·기업간계약서 시트의 보관위치 열은 GA-D6으로 뺐다
- [x] 양식 내려받기는 유형별 시트다. 자산 4종, 회사 서류, 반출 대장(과거 기록)이 대상이다 — `XD NODE_총무_가져오기양식.xlsx` 7시트(기업간계약서 포함)
- [x] 가져오기 흐름: 업로드 → 브라우저에서 읽기 → 행별 검증 결과 미리보기(오류 행 표시) → 반영. 반영은 한 batch이고 감사 행 1개에 건수만 남긴다 — PREVIEW/COMMIT(오류 행이 있으면 거부), `GA_IMPORT_COMMITTED{sheet,created,updated,skipped}`, REVERT(ga-api #13). 한 번에 500행(Design은 1,000행)
- [x] 같은 자산번호가 이미 있으면 기본은 건너뛴다. 덮어쓰기는 선택한 행만 한다 — `mode:"skip"|"overwrite"`, `overwriteRows`(ga-api #13)
- [x] 현재 장부를 엑셀로 내보낸다(`XD NODE_총무_자산대장_yyyyMMdd.xlsx` 등) — `XD NODE_총무_장부_yyyyMMdd.xlsx`, 양식과 같은 열(파일 이름 날짜가 UTC인 점은 분석 문서 §2)

**G. HR 연결**
- [x] 퇴직 정산 화면(`assets_returned` 체크 옆)에 그 직원에게 지급 중인 자산 목록과 '반납 처리' 바로가기를 둔다 — `GET /api/hr/operations?retirementAssets=`(isHrManager, 표 없으면 []), `RetirementAssetsNotice`(`app/hr-workspace.tsx:4394`), 총무 편집 권한일 때만 '총무 탭에서 반납 처리'(ga-api #14)
  - HR 편집 권한자에게만 보인다. 총무 권한이 없으면 목록만 보고 반납 처리는 막는다
- [ ] 입사 체크리스트에서 장비 지급으로 이어지는 링크를 둔다(선택) — **미구현**(선택 항목, Design에 없음)
- [x] 직원 선택은 기존 인사기록을 쓴다. 이름·부서만 필요하므로 최소 명부 라우트를 쓴다. 급여 등 PII는 보내지 않는다 — `GET /api/general/people`(사번·이름·부서·상태만, `no-store`)

### 2.2 Out of Scope
- 직원 증명서(재직·경력) 발급은 요청하지 않았다(D24)
- 결재·승인 흐름. 반출 신청→승인은 두지 않는다(D2, 2026-09-30)
- 재무 전표·계정과목 연동, 세무용 정률법 감가상각(필요하면 후속). 옛 `finance_*` 테이블 이전(데이터 0건)
- 바코드·QR 라벨 인쇄. 후속 후보이고, 자산번호는 라벨로 쓸 수 있게 짧게 만든다
- 인증서 비밀키 파일 보관(보안상 하지 않는다)
- 외부 알림(이메일·문자). 메일 서버가 없다

### 3.2 Non-Functional Requirements
- 보안
  - 첨부는 R2 `ga/<id>` 키다. 다운로드는 총무 보기 이상만 할 수 있다. `nosniff`, `Content-Security-Policy: sandbox`, 확장자 허용표를 쓴다(메신저와 같은 규칙).
  - 스캔본은 백업 단위에 포함된다.
- 날짜: 만료·D-day는 한국 시간(KST) 날짜 기준이다. 서버 시계는 UTC ms다.
- 성능: 장부는 수백~수천 행 규모다. 목록은 서버 페이지 없이 한 번에 읽는다(행 5,000개 이하 전제). 현황 계산은 1초 안에 끝나야 한다.
- 데이터: 추가만 한다. 삭제는 soft-delete이거나 '폐기' 상태다. DROP은 하지 않는다(D4).

## 7. Architecture Considerations
- 탭 추가 규칙(FR-16)을 그대로 따른다. 라우트는 `authorizeErpRequest(db, "general", …)`, 스키마는 라우트 로컬 `ensureSchema`, `db.batch`, `writeErpAudit`로 쓴다.
- 보관 태그의 고정자산 코드에서 가져오는 것은 계산기(`calculateStraightLineDepreciation`)와 화면 구조다. 계정과목 필드와 전표 연결은 버린다.
- 첨부는 메신저 첨부 헬퍼(확장자 표, `contentDisposition`, `cleanFileName`)를 공용으로 쓴다. 필요하면 `app/attachment-rules.ts`로 옮긴다.
- 메신저 알림은 채팅 서버 헬퍼(`eventStatement`, 메시지 INSERT)를 재사용한다. 시스템 작성자 표시는 DTO에서 처리한다.
