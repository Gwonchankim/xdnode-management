# 통합 재무 마스터 기획·평가·구축 기준

## 1. 문제 정의

기존 ERP는 계정과목, 거래처, 은행계좌 연결정보가 지출·예산·구매·영업 화면에 각각 존재했다. 같은 대상을 서로 다른 문자열로 입력할 수 있고, 비활성 코드가 신규 거래에 다시 쓰이거나, 코드 변경의 승인·이력이 남지 않는 위험이 있었다. 세금코드 마스터는 없었다.

## 2. 1차 기획과 평가

처음에는 기존 필드를 모두 마스터 ID로 즉시 치환하는 방안을 검토했다. 그러나 과거 전표·예산·매입/매출 문서는 당시 명칭을 증빙하는 스냅샷이므로, 전환 시 과거 표시가 바뀌거나 ID가 없는 기록이 깨질 수 있다. 또한 사업자번호가 없는 거래처를 이름 유사도로 자동 병합하면 서로 다른 법인을 합칠 위험이 있다.

## 3. 개선 기획

- 과거 문자열 스냅샷은 보존한다.
- 신규 지출·예산 입력은 활성 마스터 선택을 사용하고 API에서도 다시 검증한다.
- 계정과목·거래처·세금코드의 신규·수정·비활성·재활성 및 은행계좌-GL 연결은 전자결재 승인 후 반영한다.
- 이카운트 2025 합계잔액시산표의 코드·명칭을 계정과목 초기 기준으로 사용한다.
- Clobe 은행계좌는 전체 계좌번호 대신 소스 ID, 은행코드, 끝 4자리, 유형, 통화만 저장한다.
- 기존 영업 거래처와 구매 거래처는 정확한 사업자번호 또는 정규화된 동일 명칭만 연결한다. Clobe 외부 거래처 중 미연결 후보는 자동 병합하지 않는다.
- 실제 세금코드 목록을 받기 전에는 임의 코드를 생성하지 않는다.
- 삭제 대신 비활성화와 유효기간을 사용한다.

## 4. 데이터 구조

- `finance_master_accounts`: 계정과목, 분류, 정상잔액, 상태, 출처, 유효기간
- `finance_master_partners`: 거래처 표준명, 사업자번호, 매출/매입 유형, 지급조건, 상태
- `finance_master_partner_aliases`: 영업·구매 등 원천 레코드와 표준 거래처의 연결
- `finance_master_bank_accounts`: Clobe 계좌 메타데이터와 GL 계정 연결
- `finance_master_tax_codes`: 세금코드, 방향, 세율, 유효기간
- `finance_master_change_requests`: 변경 전후 JSON, 사유, 요청자, 결재 및 승인 이력

## 5. 통제 원칙

1. 코드 중복은 데이터베이스 고유 인덱스로 차단한다.
2. 변경 사유는 5자 이상이어야 한다.
3. 승인 전에는 운영 마스터가 바뀌지 않는다.
4. 승인 결과는 전자결재 전이 토큰을 확인한 동일 트랜잭션에서 반영한다.
5. 기존 영업·구매 거래처 생성 시 표준 거래처와 원천 별칭을 함께 만든다.
6. 신규 지출은 활성 표준 거래처와 활성 계정과목만 받는다.
7. 전기 분개 기반 예산선은 활성 계정코드가 없으면 등록하지 않는다.

## 6. 운영 점검 지표

- 활성 계정과목·거래처·세금코드 수
- Clobe 거래처 미연결 수
- 은행계좌 GL 미연결 수
- 결재 진행 중인 마스터 변경 수
- 비활성 코드 신규 참조 차단 여부
- 계정코드/명칭 불일치 차단 여부

## 7. 후속 입력 자료

- 이카운트 실제 세금코드 목록
- 은행계좌별 연결할 총계정원장 계정코드
- Clobe 거래처 중 사업자번호 또는 법인 식별값
- 실제 계정과목 사용중지·유효기간 정책
