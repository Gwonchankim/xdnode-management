# 영업 모듈 — 국내외 ERP/CRM 벤치마크 기반 다음 단계 기획

## 배경

[sales-sheet-analytics-plan.md](sales-sheet-analytics-plan.md)로 "매출 분석" 화면(월별 추이·담당자 실적·거래처 집중도·
마진율 분포·품목별 실적·수금 현황·전환 퍼널 2종)까지 구현했다. 다음 단계를 정하기 전에, 국내외 ERP/CRM이 영업
분석·파이프라인·채널관리에서 표준적으로 제공하는 기능을 조사해 XD NODE(구글시트 원천, read-only 미러, B2B·B2G
고가 장비 유통, 담당자 10명 내외)에 차용할 만한 것을 추렸다.

## 조사 요약

### 해외 ERP/CRM (Salesforce, Dynamics 365, SAP C4C, NetSuite, HubSpot, Pipedrive, Zoho)

여러 시스템에 공통적으로 나타나는 패턴:

1. **파이프라인 단계별 금액/건수 퍼널 + 단계 간 전환율(드롭 지점 탐지)** — 전 시스템 공통
2. **가중 예측 매출(Weighted Forecast) = 확률 × 금액 합산, 실시간 갱신** — Salesforce/NetSuite/HubSpot/Pipedrive 핵심 기능
3. **파이프라인 커버리지 비율(목표 대비 몇 배의 파이프라인을 확보했는지)** — HubSpot이 명시적으로 강조, 업계 벤치마크 3~5배
4. **담당자/팀별 목표 대비 달성률(쿼터 어테인먼트) + 랭킹**
5. **예측 vs 실적 괴리 하이라이트 + 룰/AI 기반 이상탐지**
6. **거래처(계정) 단위 화이트스페이스(교차판매 기회) 분석**
7. **예측 시나리오 다중화** — Zoho의 확정(Committed)/낙관(Best Case)/오픈(Open) 3단 분류가 특히 인상적. AI 확률
   계산 없이 담당자가 스스로 분류하게 하는 방식이라 데이터 정합성이 완벽하지 않은 조직에도 적용하기 쉽다.

Einstein/Copilot류 대화 인텔리전스, 이메일 감성분석, 자동 워크플로우 트리거는 콜/이메일 연동이 전제이고 "구글시트는
import-only 검증 레이어" 원칙과도 맞지 않아 제외했다.

### 국내 ERP/SFA (더존 WEHAGO, 영림원 K-System, 이카운트, 세일즈맵, 아이웍스)

- **더존 WEHAGO**: 거래처 마스터를 회계·영업·CRM이 공유, 영업목표 vs 수주실적 자동 대사, 수주 성공 시 세금계산서
  발행 데이터를 매출로 자동 연동.
- **영림원 K-System**: "사전 영업활동"을 정식 수주와 별도 프로세스로 추적 — XD NODE의 "영업보호"와 업무적으로
  가장 근접한 국내 사례.
- **세일즈맵**: 리드 파이프라인과 딜 파이프라인을 분리 관리, 단계 전이 시 자동 TODO·슬랙 알림. XD NODE의
  "인바운드 리드 → 영업보호 → 확정매출" 3단계 퍼널을 시스템적으로 이미 구현한 국내 벤치마크.

### 해외 채널관리(PRM) 솔루션의 "딜 등록" — 우리 "영업보호"와 직접 대응되는 개념

Salesforce PRM, Impartner, Channeltivity, Magentrix 등은 IT 유통·총판 업계의 "선점 등록" 관행을 훨씬 정교하게
운영한다. 핵심은 세 가지:

1. **만료 기간**: 통상 90~180일, 60~85일 시점에 자동 리마인더. 만료되면 다른 담당자가 재등록 가능.
2. **등록 시점 중복 감지**: 제출 즉시 기존 활성 등록·오퍼튜니티와 자동 대사해 충돌을 표시.
3. **거래처명을 자유 텍스트로 받지 않는다** — 이게 핵심이다. 딜 등록 폼이 마스터 계정 레코드를 검색·선택하게
   강제하고(신규면 승인 절차를 거쳐 마스터에 등록), 승인된 딜은 이후 매출까지 **같은 레코드 ID**로 추적된다.
   그래서 사후에 문자열 유사도로 매칭할 필요 자체가 없다.

**이게 바로 우리가 방금 겪은 문제의 근본 원인이다.** [sales-sheet-analytics-plan.md](sales-sheet-analytics-plan.md)의
영업보호 전환 퍼널에서 "완전일치 9.8% → 느슨한 매칭 32.5%"로 크게 벌어진 이유는, 구글 시트의 "영업보호" 탭이
거래처명을 사람이 자유 텍스트로 입력하는 구조이기 때문이다(한양대학교 vs 한양대학교 혁신창업실험실, 서울과기대 vs
서울과학기술대학교 등). 느슨한 매칭은 증상을 완화하는 임시방편이고, 성숙한 시스템들의 해법은 애초에 입력 단계에서
자유 텍스트를 없애는 것이다.

## 방향 후보

### A. 영업보호 등록의 구조적 개선 (근본 해법 — 스코프 큼)

지금 "영업보호"는 구글 시트에서 read-only로 미러링만 한다. 이 방향은 XD NODE 안에 **영업보호 등록을 위한
쓰기 가능한 화면**을 새로 만들고, 거래처명을 자유 텍스트가 아니라 `sales_accounts` 마스터 검색·선택(신규면 승인
후 마스터 추가)으로 강제하는 것이다. 구현되면:
- 지금의 "완전일치 + 느슨한 매칭" 로직 자체가 필요 없어짐 (등록 시점부터 같은 계정 ID를 참조하므로)
- 만료 기간(예: 90일) + 자동 리마인더, 등록 시점 중복 경고까지 자연스럽게 얹을 수 있음
- 단, 구글 시트가 여전히 실제 업무 도구로 쓰이고 있다면 "시트 입력 vs 앱 입력" 이원화 문제가 생긴다 — 영업팀이
  실제로 앱에서 입력하게 전환할 의지가 있는지가 전제 조건.

### B. "매출 분석" 화면 고도화 (분석 레이어 추가 — 스코프 작음, 기존 데이터로 즉시 가능)

**중요한 발견**: [sales-target-forecast-plan.md](sales-target-forecast-plan.md)로 정식 CRM(`sales_opportunities`) 쪽에
이미 "가중 파이프라인·월별 전망·달성률"(`app/sales-planning-view.tsx`, "영업 운영 > 목표·전망" 화면)이 구현돼 있다.
그런데 `/api/sales` 응답의 `dataStatus.crm`은 `NOT_CONNECTED`이고 `accounts`/`opportunities` 배열도 비어 있다 —
즉 이 정식 시스템은 기능은 있지만 실사용 데이터가 없다. 실제 영업 데이터는 전부 구글 시트 미러 테이블에 있다.
그래서 B1·B2는 "새 기능을 만든다"가 아니라 "이미 있는 정식 시스템을 시트 데이터로 채울지, 아니면 시트 쪽에
별도의 경량 버전을 둘지"를 먼저 정해야 하는 문제다.

- **B1. 가중 예측 매출**: 영업보호(느슨한 매칭 포함) → 확정매출 전환의 과거 실적 전환율을 진행 중인 영업보호/
  진행딜 금액에 곱해 "예측 매출" 라인을 월별 추이 위에 추가. 정식 CRM의 가중 파이프라인 산식과 개념은 같지만,
  시트 데이터(`sales_sheet_*`)를 원장으로 쓰는 별도의 경량 계산이 될 것.
- **B2. 파이프라인 커버리지 비율**: 담당자별/전사 (진행딜 + 영업보호 금액) ÷ 월·분기 목표. 목표 데이터 자체는
  정식 CRM 쪽 `sales_target_plans`에 이미 저장 구조가 있으므로, 여기서는 그 승인된 목표를 읽어와 시트 기반
  파이프라인과 비교하는 "교차 조회"로 구현하는 게 중복 없이 가장 자연스럽다.
- **B3. 3단계 예측 버킷 (Zoho식)**: 진행딜을 "거의 확정(예: 영업보호 progress=WIN이지만 미확정)", "가능성 있음",
  "초기 단계"로 룰 기반 분류해 합산. AI 확률 계산 없이 지금 있는 `progress`/`stage` 필드값으로 바로 구현 가능.
- **B4. 화이트스페이스(교차판매 후보)**: 거래처별 과거 구매 품목(H200/PRO 6000/DGX Spark 등)을 매핑해 "아직
  안 산 카테고리"를 노출. 대학/연구기관의 반복 구매 패턴을 활용.
- **B5. 룰 기반 이상탐지 배지**: "이번 달 신규 인바운드 리드/영업보호 등록이 최근 3개월 평균 대비 X% 하락"처럼
  임계값 기반 알림을 화면 상단에 배지로. 계산 비용이 거의 없고, 사람이 놓치기 쉬운 추세 변화를 잡아준다.

### C. 파이프라인 전이 알림 (운영 효율)

세일즈맵식으로, 리드→영업보호→확정매출 전환 시 담당자에게 알림. 다만 XD NODE는 구글 시트가 원천이라 "전이"를
시스템이 실시간으로 감지하려면 동기화 주기에 의존하게 되어 즉시성이 떨어짐 — A(구조 개선)가 선행되지 않으면
효과가 제한적.

### D. 회계 데이터 자동 대사 (장기 과제)

WEHAGO식으로 세금계산서/입금 데이터와 매출 레코드를 거래처 마스터 ID로 자동 대사. 회계 시스템 연동이 전제라
지금 범위를 크게 벗어남 — 후순위로 분류.

## 제안하는 우선순위

1. **B (매출 분석 고도화) 먼저** — 지금 있는 데이터로 바로 만들 수 있고, 방금 만든 화면에 자연스럽게 이어붙는다.
   그중에서도 B3(3단계 예측 버킷)와 B5(이상탐지 배지)가 구현 난이도 대비 체감 가치가 가장 크다고 판단. B1·B2는
   정식 CRM의 목표·전망 시스템과 개념이 겹치므로, 새로 만들기 전에 "정식 시스템을 시트 데이터로 채울지"부터
   결정하는 게 순서상 맞다(아래 열린 질문 1).
2. **A (영업보호 구조 개선)는 별도 트랙으로 분리 제안** — 매출 분석 화면 기능 추가가 아니라 "영업보호를 시트가
   아니라 앱에서 직접 등록하게 바꿀지"라는 더 큰 결정이 필요하다. 영업팀이 시트 대신 앱을 실제로 쓸 의향이
   있는지 먼저 확인하는 게 순서상 맞다.
3. **C, D는 A가 정해진 뒤에 재논의.**

## 열린 질문

1. B1(가중 예측 매출)·B2(파이프라인 커버리지)를 만들 때, 이미 있는 정식 CRM 목표·전망 시스템
   (`sales_target_plans`, `app/sales-planning-view.tsx`)을 시트 데이터로 채워 쓸지, 아니면 시트 전용의 별도
   경량 버전을 매출 분석 화면에 새로 만들지 — 두 시스템이 다른 원장(정식 영업기회 vs 시트 미러)을 보고 있어
   그대로 합치면 이중 집계 위험이 있다.
2. A(영업보호 구조 개선)를 진행한다면, 구글 시트의 "영업보호" 탭 자체를 앱 화면으로 대체할지 아니면 앱에서 등록한
   내용을 다시 시트로 역동기화할지 — 영업팀의 실제 업무 방식(시트를 계속 쓰는지)에 달려 있어 사용자 확인이 필요.
3. B4(화이트스페이스)는 품목명이 정규화되지 않은 상태([sales-sheet-analytics-plan.md](sales-sheet-analytics-plan.md)의
   품목별 실적과 동일한 한계)라, "카테고리"를 어떻게 정의할지(원문 그대로 vs 최소한의 수동 매핑 테이블) 결정이 필요.

## 결정 및 구현 완료 (B)

B1·B2·B3·B4·B5를 모두 구현했다 (A는 보류 — 영업팀의 앱 입력 전환 의향 확인 필요).

- **B1+B3 (가중 예측 매출 + 3단계 버킷)**: `getPipelineConfidence` 하나로 통합 구현. 열린 질문 없이 바로 만들 수
  있었던 이유는, 영업보호의 `progress` 필드(`WIN`/`DROP`/`0.3`/`0.5`/`0.8`)가 이미 확률 스케일과 같은 값이라 —
  진행 딜을 거래처명 느슨한 매칭(기존 전환 퍼널과 동일 로직)으로 영업보호에 연결해 그 `progress`를 확률로 재사용.
  매칭이 안 되는 진행 딜(다수)은 기본 확률 0.2로 "초기 단계" 버킷에 들어간다.
- **B2 (파이프라인 커버리지)**: 정식 CRM `sales_target_plans`/`_lines`를 읽기 전용으로 조회(쓰지 않음), 승인된
  이번 달 회사 전체 목표가 있으면 비율을 계산하고 없으면 "목표 없음"으로 표시. 담당자별 목표는 시트의 `rep`이
  자유 텍스트라 또 다른 매칭 문제가 생기므로 회사 전체 단위로만 비교.
- **B4 (화이트스페이스)**: 확정 매출 상위 10개 거래처 × 품목명 키워드 기반 7개 카테고리(H100/H200, PRO 6000,
  PRO 5000, PRO 4000/4500, RTX ADA, L4/L40, DGX/서버)로 미구매 카테고리를 노출.
- **B5 (이상탐지 배지)**: 인바운드 리드·영업보호 등록 건수를 직전 완결월 vs 그 이전 3개월 평균으로 비교해 30%
  이상 하락 시 화면 상단에 경고 배지. 기준선이 너무 작으면(평균 3건 미만) 오탐 방지를 위해 배지를 띄우지 않음.

실측 결과(2026-08-27 기준): 진행딜 합계 ₩172.5억 중 가중 예측 매출은 ₩40.8억(평균 확률 23.7%) — 대부분의 진행
