# 영업 구글 시트 통합 — 전체 기획

## 배경

영업파트가 실무에 쓰는 구글 시트("엑스디노드 공용시트")를 ERP가 직접 읽어와 반영한다.
1단계로 `26년 매출`·`진행 딜` 두 탭을 [app/sales-sheet-sync.ts](../app/sales-sheet-sync.ts)를 통해
`sales_sheet_revenue_records` 테이블에 동기화하는 기능을 만들었다 (OAuth 사용자 인증, 수동 "지금 동기화"
버튼, [app/api/sales/sheet-sync/route.ts](../app/api/sales/sheet-sync/route.ts)). 이 문서는 시트의 나머지
18개 탭을 어떻게 반영할지 정리한다.

## 시트 전체 탭 인벤토리와 분류

시트에는 총 20개 탭이 있다. 실제 헤더/샘플 행을 조회해 아래 3등급 + 제외로 분류했다.

### Tier 3 — 비정형 참고자료 (표가 아니라 자유 서식 문서 — DB 동기화 비권장)

`서버비교`(1029행/43열, 자유 텍스트+URL 섞임) · `워크견적`(견적 메모, 병합 셀·줄바꿈 텍스트) · `서버견적`/`서버견적2`(견적 작업 메모) ·
`GPU 스펙`(제품 스펙 자유 서식) · `벤치마크`(측정치 자유 서식, 다단 헤더) · `규격서`(제안서 문구) · `서버스펙 및 가격`(견적 조합표) ·
`용도별 GPU`(설명 텍스트) — 모두 사람이 참고용으로 자유롭게 편집하는 문서 형태다. 행 단위 레코드로 정규화할 근거가 약하고,
바뀌는 형태도 잦아 자동 파싱이 쉽게 깨진다. **DB 테이블화 대신, 필요하면 "구글 시트 링크만 ERP에서 바로 열기" 정도로 연결**하는 것을 제안한다.

### 제외 — 영업 데이터가 아님 (내부 계정/자격증명 관리로 추정, 민감정보)

`계정공유`, `ID 관리` — 시트 이름과 위치상 사내 로그인/계정 공유 목록으로 보인다. 영업 데이터가 아니고, 잘못 반영 시
민감정보(계정·비밀번호류) 노출 위험이 있어 이번 통합 범위에서 완전히 제외를 제안한다.

## 데이터 모델 방향

Tier 1의 나머지 5개 탭을 반영할 때, 기존 CRM 모델(`sales_accounts`/`sales_opportunities`/`sales_documents`,
[app/api/sales/route.ts](../app/api/sales/route.ts))에 편입할지, `26년 매출`/`진행 딜`처럼 시트 구조를 그대로 미러링하는
전용 테이블로 둘지 탭마다 다르게 판단했다.

- **`인바운드 영업`**: 컬럼이 리드→상담→견적→계약까지의 CRM 단계와 사실상 동일하다. `sales_opportunities`(leadType=INBOUND)로
  자동 승격하면 파이프라인 화면에 바로 잡힌다. 다만 시트의 자유 진행단계 값과 앱의 고정 `stage` enum(LEAD/DISCOVERY/PROPOSAL/CONTRACT/WON/LOST)을
  어떻게 매핑할지 결정이 필요하다 — **열린 질문 2번**.
- **`영업보호`**: 거래처를 아직 정식 등록하기 전 단계의 "선점권 등록"이라 `sales_accounts`와는 성격이 다르다. 전용 테이블
  (`sales_sheet_lead_protections`)로 미러링하는 쪽을 권장한다.
- **`서버납품`**: 이미 확정된 매출의 물류 후속 기록이라, `26년 매출` 레코드와 매출처·모델명으로 느슨하게 연결되는 전용 테이블
  (`sales_sheet_deliveries`)을 권장한다.
- **`AS`**: 기존 [docs/sales-service-control-plan.md](sales-service-control-plan.md)를 확인했다 — `SalesServiceManagement`는
  SLA 정책·전자결재·재고 반영까지 갖춘 정식 통제 워크플로다. 시트의 `AS` 탭은 그런 결재 절차 없이 현장에서 바로 기록하는
  비정형 로그라 **성격이 다르다**. 이 시트 로그를 억지로 정식 SLA 케이스로 밀어넣으면 승인·SLA 데이터를 임의로 지어내야 해서
  통제 원칙에 어긋난다. **전용 미러 테이블(`sales_sheet_service_logs`)로 별도 반영**하고, 정식 케이스 관리는 기존
  `SalesServiceManagement`를 그대로 쓰는 것을 권장한다.
- **`매입단가고지`**: `sales_catalog_items`(상품·서비스 기준정보)의 `defaultUnitPrice` 시드/참고용으로 쓰기 좋다. 다만 자동으로
  카탈로그를 덮어쓸지, "가격표 조회 전용" 별도 테이블로 둘지는 정책 결정이 필요하다 — **열린 질문 3번**.

## 재사용 가능한 기술 기반

이미 만든 [app/google-sheets.ts](../app/google-sheets.ts)의 `fetchSheetRanges`는 탭 이름만 바꾸면 그대로 재사용된다.
[app/sales-sheet-sync.ts](../app/sales-sheet-sync.ts)의 패턴(헤더 skip → 행 파싱 → 배치 upsert → `synced_at` 기준 정리 삭제)도
탭마다 반복 가능한 형태다. 개발 준비 단계에서 이 패턴을 여러 탭에 재사용하기 쉽게 일반화하는 작업(공통 파서 헬퍼, 탭별 설정만
다르게 넣는 구조)을 먼저 해두는 것을 제안한다.

## Phase 2 — 완료

Tier 1의 나머지 5개 탭을 모두 조회 전용 미러 테이블로 동기화했다. 사용자 결정: 5개 탭 한 번에 개발, 인바운드 영업은
`sales_opportunities` 자동 승격 없이 미러 테이블로만, 매입단가고지도 `sales_catalog_items` 자동 갱신 없이 별도 조회
테이블로만.

- [app/sales-sheet-sync-kit.ts](../app/sales-sheet-sync-kit.ts) — 탭 하나를 테이블 하나로 동기화하는 재사용 가능한 공통 엔진
  (설정만 다르게 넣으면 새 탭 추가 가능). `sales_sheet_sync_runs`에 `sync_key` 컬럼을 추가해 여러 동기화 파이프라인의
  이력을 한 테이블에서 공유.
- [app/sales-sheet-tabs.ts](../app/sales-sheet-tabs.ts) — 5개 탭 설정: `sales_sheet_lead_protections`(영업보호),
  `sales_sheet_inbound_leads`(인바운드 영업), `sales_sheet_deliveries`(서버납품), `sales_sheet_service_logs`(AS),
  `sales_sheet_price_catalog`(매입단가고지).
- [app/api/sales/sheet-sync/route.ts](../app/api/sales/sheet-sync/route.ts) — 기존 "지금 동기화" 버튼 하나로 매출
  원장(26년 매출/진행 딜) + 5개 탭까지 한 번에 동기화.
- [app/sales-sheet-sync-view.tsx](../app/sales-sheet-sync-view.tsx) — 탭별 요약 카드 + 최근 기록 미리보기.

실제 데이터로 검증 완료 (2026-08-26 기준): 영업보호 421건 · 인바운드 영업 617건 · 서버납품 607건 · AS 117건 ·
매입단가고지 2437건.

**알려진 사소한 데이터 특이점**: `인바운드 영업` 시트 중간에 "여기서부터 내부 ERP로 업무이관 입니다" 같은 사람이 남긴
안내문이 리드 행처럼 섞여 들어간다 (회사/담당자 칸은 비어 있어 실제 리드와 쉽게 구분됨). 특정 문자열을 하드코딩해
걸러내기보다 화면에서 육안으로 걸러지는 수준이라 그대로 두었다.

## 다음 단계 (미착수)

1. **Phase 3** — Tier 2(`GPU가격표`, `sw갱신관리`) 섹션 인식 파서 개발. `GPU가격표`는 카테고리 섹션마다 헤더가
   반복되는 구조라 별도 설계가 필요하다.
2. **보류/제외** — Tier 3 문서 탭(`서버비교`/`워크견적`/`서버견적`/`서버견적2`/`GPU 스펙`/`벤치마크`/`규격서`/
   `서버스펙 및 가격`/`용도별 GPU`)은 DB화하지 않고 필요 시 링크만 노출하는 방향을 유지. `계정공유`/`ID 관리`는 계속 제외.
