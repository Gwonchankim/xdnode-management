# 기준정보 위험 주간보고 확인·승인 기획

## 1. 현행 평가

- 주간 위험 보고는 버전과 SHA-256 체크섬으로 보존되지만, 누가 조직장 응답을 확인했는지와 어떤 보완조치가 이어졌는지 기록하지 못했다.
- 전자결재와 통합 업무함은 이미 서버 원장으로 운영되므로 별도 임시 승인 UI를 만들면 승인 이력이 분산된다.
- 현재 로그인 권한은 대표 계정 1명뿐이다. 조직장이 직접 로그인해 승인한 것처럼 표시하면 사실과 다른 감사기록이 된다.

## 2. 개선된 운영 원칙

1. 보고서의 `snapshot_json`과 `checksum`은 생성 후 수정하지 않는다.
2. 조직장별 응답은 별도 확인 원장에 기록한다. 조직장과 실제 기록자를 구분해 보존한다.
3. 보완이 필요한 응답은 회사 재직자 한 명과 기한을 지정한 후속업무를 통합 업무함에 만든다.
4. 후속업무가 `DONE`이 되기 전에는 해당 조직장 확인을 완료할 수 없다.
5. 모든 조직장 확인이 완료되어야 경영 책임자 전자결재를 제출할 수 있다.
6. 승인·반려는 기존 전자결재 엔진을 사용하고, 자동 승인·자동 종결은 하지 않는다.
7. 같은 보고서에는 전자결재를 하나만 연결한다. 반려된 보고서는 고치지 않고 새 스냅샷 버전을 만든다.
8. 현재 권한 구조의 동일인 기안·승인 가능성은 숨기지 않으며, 조직장 응답의 실제 기록자도 화면에 표시한다.
9. 불변 보고서는 전자결재의 보완 재제출·기안 취소를 허용하지 않는다. 승인 또는 반려로 종결하고 보완이 필요하면 새 스냅샷 버전을 만든다.
10. `snapshot_json`과 `checksum` 변경은 API뿐 아니라 데이터베이스 트리거에서도 거부한다.

## 3. 상태 흐름

`DRAFT(조직장 확인 중) → SUBMITTED(경영 책임자 결재) → APPROVED 또는 REJECTED`

조직장 확인은 다음 상태를 가진다.

`PENDING → ACKNOWLEDGED`

또는

`PENDING → ACTION_REQUIRED → 후속업무 DONE → ACKNOWLEDGED`

## 4. 저장 원장

- `erp_master_impact_weekly_reports`: 불변 보고 본문과 별도 워크플로 상태
- `erp_master_impact_weekly_report_reviews`: 조직장별 응답·보완 담당자·기한·실제 기록자
- `erp_master_impact_weekly_report_events`: 생성·확인·보완·제출·승인·반려의 추가 전용 이력
- `erp_tasks`: 후속조치와 전자결재 알림
- `erp_approval_requests`, `erp_approval_steps`, `erp_approval_events`: 경영 책임자 전자결재
- `erp_audit_logs`: 사용자 행위의 전후 상태

## 5. 검증 기준

- 보고 본문과 체크섬을 바꾸는 UPDATE 경로가 없어야 한다.
- 조직장별 확인 행은 보고서와 조직장 조합으로 중복될 수 없어야 한다.
- 같은 보고서에 둘 이상의 전자결재를 만들 수 없어야 한다.
- 보완업무 완료 전 확인 완료가 거부되어야 한다.
- 미확인 조직장이 남으면 전자결재 제출이 거부되어야 한다.
- 승인 결과가 보고 상태와 추가 전용 이벤트에 연결되어야 한다.
- 불변 보고서의 보완 요청·재제출·취소가 거부되어야 한다.
- 직접 SQL로 보고 본문이나 체크섬을 수정하려 해도 데이터베이스가 거부해야 한다.
- 권한, 낙관적 잠금, 마이그레이션, 전체 회귀 및 배포 빌드가 통과해야 한다.
