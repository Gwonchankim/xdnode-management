# XD NODE ERP 통합 제품 기획서

## 1. 제품 목표

XD NODE ERP는 재무회계, 영업, HR의 데이터를 한 화면에 모으는 대시보드가 아니라 다음 업무를 실제로 처리하는 운영 시스템을 목표로 한다.

1. 모든 수치는 출처와 기준일을 확인할 수 있다.
2. 사용자는 자신에게 허용된 업무만 조회하거나 변경할 수 있다.
3. 주요 변경은 작업자, 변경 전후 값, 시각이 기록된다.
4. 알림은 고정 문구가 아니라 실제 데이터와 업무기한에서 생성된다.
5. 재무·영업·HR의 동일 인물과 거래처는 하나의 기준정보를 사용한다.
6. AI는 근거를 제시하고 초안을 만들지만, 회계·인사·급여를 임의 확정하지 않는다.

## 2. 현행 평가

### 실제 운영 데이터가 연결된 영역

- 2024~2025년 결산 재무자료와 2026년 Clobe 재무 스냅샷
- 재무 매입·매출 순위, 손익·재무상태, 유동성 위험 신호
- 외상매출금 담당자·회수예정일·상태·메모 저장
- HR 직원정보, 조직 및 조직장, 지원자, 채용담당자
- 면접 및 면담 녹음파일 저장
- 2025~2026년 급여 원본 기록 조회
- Cloudflare AI를 이용한 이력서 분석과 재무 질의

### 부분 구현 영역

- 사용자 목록은 저장되지만 실제 API 권한과 완전히 연결되지 않음
- 알림 일부는 실제 상태가 아니라 고정된 문구와 수치에서 생성됨
- 재무자료는 소스 파일을 갱신하고 다시 배포해야 최신화됨
- 급여는 과거 자료 조회 중심이며 계산·승인·마감 흐름은 없음
- 면접 및 면담 전사는 브라우저 기능에 의존하는 부분이 있음

### 시연 데이터 또는 미구현 영역

- 영업 KPI, 영업기회, 인센티브 지급현황
- 근태, 휴가, 성과, 교육, 인력계획의 일부 화면
- 빠른 등록의 임시저장 동작
- 통합검색, 첨부문서 버전, 휴지통, 일괄처리

## 3. 개선된 구축 원칙

### 3.1 데이터 갱신과 프로그램 배포 분리

- Clobe 동기화 결과를 D1의 불변 스냅샷으로 저장한다.
- 데이터 동기화는 매일 수행하지만 기능 배포는 코드가 변경된 경우에만 수행한다.
- 동기화 실행마다 시작·종료 시각, 성공 여부, 원천 건수, 합계, 오류를 기록한다.
- 동일 원천자료의 중복 반영을 방지하는 식별자와 해시를 저장한다.
- 현재 스냅샷과 이전 스냅샷을 비교하며 필요할 경우 이전 자료로 복구할 수 있다.

### 3.2 실제 데이터 상태 표시

모든 주요 카드와 표에는 다음 중 하나를 표시한다.

- `LIVE`: 원천 시스템에서 갱신되는 실제 데이터
- `IMPORTED`: 사용자가 업로드하고 대사한 확정 자료
- `MANUAL`: 사용자가 ERP에서 직접 입력한 자료
- `DEMO`: 시연 데이터이며 운영 판단에 사용하면 안 되는 자료
- `NOT CONNECTED`: 필요한 원천자료가 아직 연결되지 않은 상태

### 3.3 권한과 감사

역할은 중복 부여할 수 있으며 권한 판정은 서버에서 수행한다.

| 역할 | 주요 권한 |
|---|---|
| 대표자 | 전체 조회, 주요 승인, 권한관리 |
| 재무관리자 | 재무 조회·입력·대사·마감 |
| HR관리자 | 인사·급여·채용 관리 |
| 채용담당자 | 배정된 지원자와 면접 관리 |
| 영업관리자 | 거래처·영업기회·견적·수주 관리 |
| 조회전용 | 허용된 모듈 조회와 내보내기 |

감사기록에는 작업자, 기능, 대상, 변경 전후 값, 사유, 시각, 요청 식별자를 저장한다. 삭제는 기본적으로 복구 가능한 소프트 삭제로 처리한다.

## 4. 통합 업무 모델

### 4.1 통합 업무함

- 나에게 배정된 업무
- 승인 대기
- 기한 초과
- 데이터 확인 필요
- 동기화 오류
- 읽지 않은 알림
- 관련 화면 바로가기
- 처리 메모와 완료 시각

### 4.2 실제 상태 기반 알림

알림 규칙의 예시는 다음과 같다.

- 분개 차대변 불일치 발생
- 계정과목이 없는 은행거래 발생
- 7일 이내 현금 부족 예상
- 미수금 회수예정일 경과
- 급여 마감 체크리스트 미완료
- 지원자 단계별 기한 초과
- 입사·퇴사 체크리스트 기한 임박
- 휴가 승인 지연
- 조직장 미지정

단순 정보 알림은 확인 후 종료할 수 있고, 조치가 필요한 알림은 관련 업무가 완료되어야 종료된다.

## 9. 검증 시나리오

각 기능은 아래 근거가 모두 있어야 완료로 판정한다.

1. 새로고침 후 데이터가 유지된다.
2. 권한 없는 사용자의 API 요청이 거부된다.
3. 변경 후 감사기록이 생성된다.
4. 실제 데이터와 시연 데이터가 혼동되지 않는다.
5. 연결된 모듈에서 동일한 기준정보가 표시된다.
6. 실패 시 부분 저장 없이 사용자에게 원인이 표시된다.
7. 키보드와 좁은 화면에서도 주요 작업이 가능하다.
8. 빌드, 스키마, 데이터 대사, 주요 업무 시나리오 테스트가 통과한다.

## 11. 2차 구축·평가 결과

이번 회차에서 다음 업무를 실제 저장형 기능으로 전환했다.

- 근태 수기기록과 휴가 신청·승인: 자료 출처를 `MANUAL`로 명시하고 승인 업무를 통합 업무함에 연결
- 직원 문서: PDF·DOCX·XLSX·이미지·텍스트 업로드, 유형별 버전, 다운로드 이력, 복구 가능한 삭제
- 영업 문서: 영업기회에 견적·수주·납품·청구·수금을 연결하고 확정·완료에 승인권한 적용
- 상태 기반 업무: 담당자 미지정·7일 이상 정체 지원자, 미마감 급여, 차대변 불일치를 실제 데이터로 생성하고 해결 시 자동 종료

평가 기준은 새로고침 유지, 권한검사, 감사기록, 출처 표시, 스키마 일치, 빌드와 회귀테스트 통과다. 다음 루프는 근태기기·전자결재·전자세금계산서 같은 외부 원천을 연결하고, 수기 자료와 자동연동 자료의 대사를 추가하는 단계다.

## 12. 3차 구축·평가 결과 — 공통 전자결재 — 대체됨 (xdnode-management D2)

> **대체됨 (xdnode-management D2)** — 2026-09-28 R1에서 전자결재(승인 엔진·결재 API·결재함)를 삭제했다(D2-개정). HR 상태 전환은 편집 권한자가 즉시 반영하고(D2-a, `app/hr-transitions.ts`), 감사 기록(`writeErpAudit`)은 그대로 남는다. 이 절은 기록으로만 남긴다. 코드는 보관 태그 `erp-final-20260923`에 있다. 현재 범위는 `docs/01-plan/features/xdnode-management.plan.md`를 본다.

기존 모듈별 상태 변경을 공통 결재 원장으로 통합했다.

- 결재 문서: 업무 영역, 유형, 기안자, 금액, 우선순위, 기한, 연결 원문과 버전
- 결재선: 순서, 단계명, 필요 역할, 실제 결재자, 처리 상태와 의견
- 처리 이력: 제출, 승인, 반려, 보완 요청, 재제출, 취소를 수정 불가능한 사건으로 보관
- 동시성: 사용자가 열어둔 문서 버전과 서버 버전이 다르면 처리를 거부하고 새로고침 안내
- 권한: 기안은 모듈 쓰기 권한, 승인·반려는 해당 모듈 승인 권한과 현재 단계 결재자 여부를 모두 검사
- 원 업무 연결: 휴가, 인사 발령, 급여월, 예산, 월마감, 영업 문서의 최종 상태를 결재 완료 시 같은 처리 묶음에서 반영
- 인사 발령 안전장치: 제출 시 직원의 현재 소속·직급은 유지하고, 최종 승인된 발령만 인사기록과 변경이력에 반영
- 업무함 연결: 현재 결재자의 통합 업무를 자동 생성하고 결재 처리 전에는 임의 완료를 차단

현재 회사에서 ERP 권한이 부여된 사용자가 한 명이므로 실제 결재선은 김권찬 관리자에게 귀결될 수 있다. 사용자 권한이 추가되면 역할별 결재자가 자동 배정되며, 다음 평가 루프에서는 금액·부서·예외 조건별 결재선 설정 화면과 대결·전결 규칙을 추가한다.

## 13. 4차 구축·평가 결과 — 결재 운영규칙과 시행일 통제 — 대체됨 (xdnode-management D2)

> **대체됨 (xdnode-management D2)** — 2026-09-28 R1에서 결재 운영규칙(approval-settings)을 삭제했다(D2-개정). 인사발령의 시행일 대기와 1회 적용은 `app/hr-personnel-actions.ts`가 계속 맡는다. 이 절은 기록으로만 남긴다. 코드는 보관 태그 `erp-final-20260923`에 있다. 현재 범위는 `docs/01-plan/features/xdnode-management.plan.md`를 본다.

코드에 고정돼 있던 결재선을 운영 데이터로 관리할 수 있게 확장했다.

- 금액·유형별 규칙: 업무 영역, 결재 유형, 최소·최대 금액, 우선순위와 최대 3단계 결재선을 저장
- 전결: 한 단계만 둔 규칙은 해당 결재자의 승인으로 최종 확정
- 지정 결재자: 역할 자동배정 외에 활성 ERP 사용자를 단계별로 지정 가능
- 규칙 선택: 제출 금액에 맞는 활성 사용자 규칙을 우선 적용하고, 없으면 검증된 기본 결재선 사용
- 결재선 스냅샷: 제출 당시 적용 규칙과 실제 결재자를 사건 이력에 저장해 이후 규칙 변경이 진행 중 문서를 바꾸지 않음
- 대결: 원 결재자, 대결자, 업무 범위, 시작·종료일, 사유를 저장하고 새로 제출되는 결재에만 적용
- 대결 권한: 일반 승인권한을 광범위하게 주지 않고, 대결로 배정된 특정 단계만 처리 가능
- 지연 통제: 내 결재 중 기한이 지난 문서를 별도 지표와 강조표시로 제공
- 인사 시행일: 미래 시행 인사발령은 승인 상태로 대기하고, 시행일이 도래한 뒤 한 번만 직원 소속·직급과 변경이력에 반영

운영 안전장치는 겹치는 금액 구간과 중복 대결기간 차단, 활성 사용자만 지정, 모든 설정 변경 감사기록, 기존 결재 문서의 결재선 불변이다. 다음 루프에서는 지출·지급·퇴직·채용 제안 업무 자체를 공통 전자결재와 연결하고 증빙 문서 및 회계 원장 반영까지 이어간다.

## 14. 5차 구축·평가 결과 — 결재 이후 원장 연결

### 지출·지급

- 지출 결의 또는 지급 요청 초안을 만들고 영수증·세금계산서 등의 증빙을 첨부한다.
- 증빙이 없는 요청은 결재를 제출할 수 없고, 최종 승인 전에는 지급원장에 기록할 수 없다.
- 승인 후 재무 승인 권한자가 지급일·지급수단·은행 참조값을 기록한다. 요청당 지급은 한 번만 허용한다.
- 지급 완료 요청은 `PAID`, 회계 상태는 `READY`가 된다. `READY`는 분개 완료가 아니라 분개 준비 상태이므로 실제 전표 연결 전에는 임의 기장하지 않는다.

### 퇴직

- 퇴직일·사유·인사담당자 및 퇴직자 체크리스트를 하나의 퇴직 요청으로 기안한다.
- 결재 전에는 직원 상태를 바꾸지 않는다. 승인 후 `퇴직 예정`으로 바꾸고 체크리스트를 활성화한다.
- 체크리스트가 모두 완료되었고 퇴직일이 도래한 경우에만 `퇴직`으로 전환한다. 미래 퇴직일이면 대기하다 조회 시점에 한 번만 반영한다.
- 반려 시 체크리스트 업무는 취소되고 기존 인사기록은 유지된다.

### 채용 제안

- 면접 상세 화면에서 제안 직무·소속·고용형태·입사예정일·연봉·수습기간을 기안한다.
- 동일 지원자에게 진행 중 또는 승인된 제안이 있으면 중복 기안을 막는다.
- 최종 승인 결과에 따라 지원자 단계가 `채용 제안 승인` 또는 `채용 제안 반려`로 자동 반영된다.
- 연봉과 처우 정보는 일반 메모가 아닌 별도 채용 제안 원장에 보존하고 기안·승인 결과를 감사기록에 남긴다.

## 15. 6차 구축·평가 결과 — 승인 이후 업무 완료

### 지급에서 회계전표까지

- 지급 완료 건마다 회계전표는 하나만 생성하며 전표일·적요·차변·대변 계정을 사용자가 확인해야 한다.
- 계정은 시스템이 임의 확정하지 않는다. 요청 계정과 보통예금을 입력 제안값으로 보여주되 사용자가 확정한 뒤 `DRAFT` 전표를 만든다.
- 재무 승인 권한자가 차변·대변과 동일 금액을 재확인한 뒤 전기하며, 요청과 전표를 같은 처리 묶음에서 `POSTED`로 바꾼다.
- 전표 생성과 전기는 감사기록에 남고, 중복 생성과 중복 전기를 차단한다.

### 채용 제안에서 입사까지

- 승인된 채용 제안에 지원자 수락 또는 거절 회신을 기록한다.
- 수락 시 신규 사번·직급·직책을 필수 확인하고, 입사예정 인사기록과 근로계약·계정·장비·오리엔테이션 업무를 동시에 생성한다.
- 모든 온보딩 필수 업무가 완료되고 입사일이 도래한 경우에만 `입사 예정`에서 `재직`으로 한 번 전환한다.
- 재직 전환된 온보딩 업무는 되돌리지 못하며, 입사 전환된 지원자는 채용 화면에서 삭제하지 않고 인사기록에서 관리한다.

### 퇴직 승인에서 정산·회수까지

- 퇴직 승인 시 별도 정산 원장을 만들고 최종 급여·퇴직금·미사용 연차수당·공제액과 순정산액을 보존한다.
- 급여 확인, 4대보험 상실 신고, 업무 계정 회수, 회사 자산 반납, 업무 인수인계 다섯 통제를 모두 완료해야 정산이 `READY`가 된다.
- 기존 퇴직 체크리스트도 모두 완료되고 정산이 `READY`인 경우에만 퇴직 요청을 완료할 수 있다.
- 미래 퇴직일 자동 반영도 정산 상태를 다시 확인하므로, 완료 요건이 뒤늦게 해제된 건은 자동 퇴직 처리하지 않는다.

검증은 41개 테이블 마이그레이션, 요청별 전표 유일성, 정산 원장 기본값, 권한·상태 가드, 원자적 상태 전이, 빌드와 32개 회귀 테스트로 수행한다.

## 16. 7차 구축·평가 결과 — 급여 마감에서 지급·전표까지

- 급여 상태는 `작성 중 → 검토 요청 → 승인 완료 → 마감 잠금` 순서로만 진행하며, 중간 단계를 건너뛰는 변경을 서버에서 차단한다.
- 승인 완료 급여월을 마감하면 기록상 지급액 합계로 재무회계 지급대기 원장을 한 건만 생성한다. 원천 유형과 급여월을 저장해 HR 급여월과 재무 요청을 다시 추적할 수 있다.
- 제공 자료에서 급여 계정코드가 확정되지 않았으므로 코드를 임의 부여하지 않는다. 지급 건에는 `급여(계정 확인 필요)`를 표시하고 전표 생성 시 사용자가 실제 차변 계정을 확인한다.
- 급여 지급 건은 이미 HR 전자결재를 통과했으므로 재무 원장에는 승인 완료 상태로 연결하지만, 실제 지급은 재무 승인 권한자가 지급일·지급수단·은행 참조값을 확인해야 완료된다.
- 미지급·미전표 상태에서는 사유를 남기고 급여월을 재개방할 수 있으며 연결 지급 건은 취소된다. 이미 지급했거나 전표 생성이 시작된 경우에는 단순 재개방을 차단하고 재무 취소·역분개 절차를 요구한다.
- 재무 화면은 급여에서 자동 생성된 지급 건을 별도 표기하고, 마감·재개방·지급·전표 이력을 감사기록에 남긴다.

## 17. 8차 구축·평가 결과 — 청구에서 부분수금·미수금까지

- 수금 문서는 반드시 같은 영업 건의 `확정` 또는 `완료` 청구서를 하나 선택해 등록한다. 문서번호만 비슷한 거래를 자동 연결하지 않는다.
- 청구서와 수금 문서 사이에 별도 배분 원장을 두어 청구액, 작성·결재 중 수금 예약액, 승인·완료된 확정 수금액, 현재 미수잔액을 구분한다.
- 한 청구서에 여러 번 부분수금할 수 있지만, 한 수금 문서는 한 청구서에 한 번만 배분한다. 향후 다수 청구서 일괄입금 기능은 별도 배분 UI를 추가할 때 확장한다.
- 작성·결재 중인 수금도 청구잔액을 예약하므로 여러 사용자가 동시에 수금을 등록해 청구액을 초과하는 것을 차단한다. 취소된 초안은 예약액에서 제외한다.
- 확정 수금만 실제 수금 합계와 미수잔액에 반영한다. 확정·완료 수금은 단순 취소를 허용하지 않고 역수금·환불 절차를 요구한다.
- 영업 화면에서 확정 청구, 확정 수금, 현재 미수금, 수금 예약을 함께 보여주고 청구 행에는 완납 또는 남은 미수금, 수금 행에는 연결 청구번호를 표시한다.

## 18. 9차 구축·평가 결과 — 구매에서 매입채무·지급까지

- 매입 거래처 마스터에 사업자번호, 담당자, 이메일, 지급조건을 저장하고 중복 사업자번호 등록을 차단한다.
- 발주서는 최대 20개 품목의 수량·단가·공급가액과 사용자가 입력한 세액을 별도 품목행으로 보존한다. 발주금액은 서버에서 다시 계산하며 발주번호는 중복될 수 없다.
- 발주는 공통 전자결재를 통과해야 입고·검수를 등록할 수 있다. 승인 전 발주를 검수 또는 지급 단계로 넘기지 않는다.
- 입고·검수는 품목별 입고수량, 합격수량, 불합격수량을 기록하고 누적 합격수량이 발주수량을 초과하지 못하게 한다. 모든 품목이 충족되면 발주를 입고 완료로 전환한다.
- 매입 인보이스는 발주 공급가 잔액과 `합격 검수수량 × 발주단가` 잔액을 각각 비교한다. 둘 중 하나라도 초과하면 지급하지 않고 대사 예외와 원인을 표시한다.
- 부분 입고·부분 인보이스를 허용하되 취소되지 않은 기존 인보이스 금액을 잔액에서 차감한다. 인보이스번호 중복도 데이터베이스에서 차단한다.
- 3자 대사가 일치한 인보이스만 재무 지급 요청 초안을 만들 수 있다. 지급 요청에는 원천 인보이스 식별자를 보존하고 증빙 첨부·전자결재·지급·전표 절차를 그대로 거친다.
- 실제 지급 시 매입 인보이스도 같은 처리 묶음에서 지급 완료로 바뀌며, 재무 화면에는 구매 인보이스 자동연결 건으로 표시된다.

## 19. 10차 구축·평가 결과 — Clobe 은행 거래와 ERP 자금 대사

### 평가

- 기존 `finance_reconciliations`는 빈 상태 테이블과 준비 안내만 제공해 실제 거래별 대사를 수행할 수 없었다.
- Clobe 2026년 8월 원문에는 계좌 간 이체, 외화 거래, 미분류 거래와 일반 수금·지급이 함께 존재하므로 금액 일치만으로 자동 확정하면 오분류 위험이 컸다.
- ERP 내부에는 지급원장과 수금원장이 이미 존재하므로 은행 원문을 불변으로 보관하고 별도 배분 원장으로 연결하는 방식이 적합했다.

### 개선된 기획

- Clobe 거래 ID를 기본키로 사용해 원문 156행에서 중복 1행을 제거한 155건을 저장한다.
- 전체 계좌번호는 저장하지 않고 은행·계좌명·끝 4자리만 운영 화면에 제공한다.
- 금액·거래일·적요·거래처를 점수화해 후보만 제안하며 자동으로 완료 처리하지 않는다.
- 한 은행 거래를 여러 ERP 지급·수금 원장에 부분 배분할 수 있지만 어느 쪽 잔액도 초과할 수 없다.
- 같은 시각·금액의 반대 방향 거래는 내부 이체 후보로 제시하고 양쪽 거래를 하나의 대사 그룹으로 확정한다.
- 대사 확정·비대상 처리·해제는 담당자·시각·사유와 함께 감사로그에 남긴다.
- 해당 월 원화 거래가 미대사 상태이면 월마감의 은행 대사 업무를 완료·승인할 수 없다.

### 구축 및 검증

- `finance_bank_transactions`, `finance_cash_matches` 원장을 추가했다.
- 재무회계 좌측 메뉴에 `자금 대사` 전용 화면을 추가하고 미처리·미분류·완료·내부 이체 필터를 제공한다.
- 지급원장·확정 수금원장·상대 계좌 거래 후보를 제시하며 수동 원장 선택, 부분 금액 입력, 비대상 처리, 대사 해제를 지원한다.
- 미대사 거래가 존재하면 알림 센터에 상태 기반 업무를 생성하고 모두 해결되면 자동 완료한다.
- 거래 ID 중복 제거, 부분 배분 합계, 중복 원장 연결 차단, 대사 해제 후 잔액 복원, 월마감 차단을 회귀 테스트로 검증한다.

## 20. 11차 구축·평가 결과 — 13주 자금예측 자동화

### 평가

- 기존 재무 운영센터의 자금예측은 수기 예정 항목만 합산하므로 실제 미수 청구서, 매입 인보이스, 결재 중 지급 요청과 급여 지급을 빠뜨릴 가능성이 있었다.
- 같은 매입 인보이스가 지급 요청으로 전환된 뒤 두 원천을 함께 집계하면 현금 유출이 중복되며, 수금 예약이 잡힌 청구서를 전액 미수금으로 계산해도 중복 예측이 발생한다.
- 지급예정일이 없는 원천에 임의 날짜를 부여하면 숫자는 완성돼 보이지만 실제 자금 위험을 왜곡하므로, 누락과 대체 날짜를 별도 품질 문제로 보여줘야 한다.

### 개선된 기획

- 13개 주차는 Clobe 최신 기준일부터 91일을 포괄한다. 첫 주에는 기준일 이전 미처리 예정도 연체 항목으로 포함한다.
- 원천 우선순위는 `지급·지출 요청 → 연결 전 매입 인보이스`, `청구서 잔액 → 취소되지 않은 수금 예약 차감`, `발생 원장이 없는 수기 계획` 순으로 적용한다.
- 지급 요청에 지급예정일이 없으면 요청일을 임시 대체하되 화면에 `요청일 대체`로 표시한다. 어느 날짜도 없으면 예측에서 제외하고 보완 목록과 알림에 남긴다.
- 기준·보수·낙관 시나리오는 동일 원천의 확률만 조정한다. 보수 시나리오는 유입확률을 낮추고 유출은 100% 반영하며, 낙관 시나리오는 유입확률만 높인다.
- 최소운영자금, 기본 시나리오, 미수금 회수확률, 외화예금 포함 여부는 D1 설정으로 영구 저장한다. 최소운영자금은 회사가 정하기 전까지 0원으로 두고 시스템이 임의 가정하지 않는다.
- 주차별 유입·유출·기말잔액뿐 아니라 해당 합계를 구성한 원장, 적용확률, 예정일, 요청일 대체 여부를 같은 화면에서 추적한다.

### 구축 및 검증

- `finance_cash_forecast_settings`, `finance_cash_forecast_snapshots`를 추가하고 같은 기준일·시나리오의 스냅샷은 갱신하되 중복 행을 만들지 않는다.
- 재무회계 좌측 메뉴에 `13주 자금예측` 전용 화면을 추가하고 설정, 세 시나리오, 주차별 차트·표, 근거 원장, 품질 경고, 수기 계획 입력을 제공한다.
- 최소운영자금 하회 또는 예정일 누락이 있으면 알림 센터에 상태 기반 업무를 생성하고 위험이 해소되면 자동 완료한다.
- 매입 인보이스와 지급 요청 중복 제외, 수금 예약 차감, 누락·대체 날짜 구분, 시나리오 확률, 일별 스냅샷 유일성, 설정 저장, 운영 빌드와 전체 회귀 테스트로 검증한다.

## 21. 12차 구축·평가 결과 — 기간 단위 월마감 통제

### 평가

- 기존 월마감은 다섯 개 체크리스트를 각각 완료·승인하는 구조여서 월 전체가 실제로 잠겼는지, 어떤 원장과 증빙으로 승인했는지 한 번에 증명할 수 없었다.
- 은행 대사 외의 항목은 사용자가 원장 문제를 해결하지 않고도 완료 처리할 수 있었고, 승인된 월의 증빙 변경과 재개방에 대한 기간 단위 통제가 없었다.
- Clobe 월별 분개 집계가 없는 과거 월까지 자동 통과로 간주하면 잘못된 확신을 주므로, 확인할 수 없는 범위는 수동 검토로 명시해야 한다.

### 개선된 기획

- `finance_close_runs`를 월별 단일 실행 원장으로 두고 작성 중, 결재 진행, 마감 잠금 상태와 버전, 제출·승인·재개방 이력을 보존한다.
- 원화 은행거래 대사, Clobe 차대변 차이, ERP 미전기 전표, 지출 증빙 누락, 급여월 잠금은 원장을 조회해 자동 판정한다.
- 채권채무, 세금계산서·부가세, 월 손익·재무상태표는 담당자 수동 검토로 남기며 과거 월의 Clobe 차대변도 월별 원장 증빙을 첨부해 확인한다.
- 자동 통제 실패가 0건이고 수동 검토가 모두 완료됐으며 마감 증빙이 한 건 이상 있어야 월 전체 잠금 결재를 제출할 수 있다.
- 제출 시 자동 통제, 수동 검토, 증빙 건수와 기준일을 JSON 스냅샷으로 동결한다. 제출·잠금 상태에서는 업무와 증빙을 변경할 수 없다.
- 잠금 해제는 사유를 필수로 받아 별도 전자결재를 거치며 승인되면 버전을 올리고 다시 작성 중 상태로 전환한다.

### 구축 및 검증

- 재무회계 좌측 메뉴에 `월마감 통제` 전용 화면을 추가하고 마감월, 자동 통제, 수동 검토, 차단 사유, 마감 증빙, 잠금·재개방 작업을 제공한다.
- 월마감 통제가 남으면 알림 센터에 상태 기반 업무를 만들고 잠금 또는 해결 시 자동 완료한다.
- 기간 실행 유일성, 원장 기반 자동 판정, 제출 전 필수조건, 잠금 후 변경 차단, 스냅샷 보존, 재개방 승인과 버전 증가를 회귀 테스트로 검증한다.

## 22. 13차 구축·평가 결과 — 예산 대비 실적 통제

### 평가

- 기존 `finance_budgets`는 월별 한 줄마다 상태와 승인을 관리해 연간 계획 전체가 하나의 승인 버전이라는 사실을 보장하지 못했다.
- 실제값 원천이 연결되지 않아 예산 초과, 수익 미달, 연말 전망을 신뢰할 수 있는 근거로 계산할 수 없었다.
- Clobe 원천에는 부서 코드가 없으므로 부서 예산을 0원 실적으로 처리하면 잘못된 경보가 만들어진다.

### 개선된 기획

- `finance_budget_plans`는 연도별 계획 버전과 승인·개정 상태를 보관한다. 신규 승인 시 같은 연도의 이전 승인본은 `SUPERSEDED`로 전환하되 삭제하지 않는다.
- `finance_budget_plan_lines`는 월·부서·계정·수익/비용 구분·실적 원천·허용 차이율을 명시한다.
- 실적 원천은 Clobe 매출·매입 세금계산서와 ERP 전기 분개 차변·대변으로 제한한다. 부서 코드가 없는 원천은 `전사` 예산만 자동 연결한다.
- 현재월은 기준일까지 예산을 일할 계산해 월초 수익 미달 오경보를 줄인다. 수익은 미달, 비용은 초과를 서로 다른 방향으로 판정한다.
- `finance_budget_variance_actions`에는 차이 원인, 조치 계획, 담당자, 기한, 처리 상태를 한 예산선당 하나의 최신 통제 원장으로 저장한다.
- 승인 예산 개정은 원본을 복제한 새 버전에서 수행하고 개정 사유를 필수로 남긴다.

### 구축 및 검증

- 재무회계 사이드바에 `예산·실적` 전용 화면을 추가한다.
- 연간 예산, 기준일까지 비교 예산, 실제 발생액, 실적 매핑률, 수익·비용별 연말 예상, 경보·주의·매핑 필요 건수를 표시한다.
- 실제값이 연결되지 않은 예산은 0원이 아니라 `매핑 필요`로 표시한다.
- 승인된 현재월 예산이 허용범위를 벗어나고 조치가 완료되지 않으면 알림센터에 `budget-variance-alert`를 생성한다.
- 연도·버전 중복, 예산선 실적 매핑 중복, 차이조치 중복을 SQLite 고유 인덱스로 차단한다.
- 작성 중 계획만 예산선을 추가·삭제할 수 있고, 승인본은 개정본을 통해서만 변경한다.
- 결재 승인 시 이전 승인본 전환과 신규 승인본 확정을 같은 승인 처리 묶음에서 수행한다.

## 23. 14차 구축·평가 결과 — 통합 감사·변경이력

### 평가

- 주요 쓰기 API는 이미 공통 감사 원장에 처리자, 대상, 변경 전후 값과 사유를 남겼지만 운영 화면에서는 CSV를 만든 뒤 내려받아야만 조사할 수 있었다.
- 통합 업무함은 미처리 업무를 찾는 기능이고, 이미 처리된 업무의 책임과 변경 근거를 추적하는 기능은 아니었다.
- 감사 JSON 전체를 검색하거나 무제한 조회하면 개인정보 노출과 전수검색 부하가 커질 수 있었다.

### 개선된 기획

- 데이터 통제 센터 안에 관리자 전용 읽기 화면을 두어 별도의 중복 메뉴를 만들지 않는다.
- 기간·업무 영역·작업·처리자·대상·사유를 검색하되 변경 JSON 원문은 검색 대상에서 제외한다.
- 30건 단위 `(created_at, id)` 커서 페이지네이션으로 동일 시각 기록도 안정적으로 이어 본다.
- 비밀번호·토큰·인증 헤더 등 보안 키 값은 서버에서 가린 뒤 응답한다.
- 조회는 원장을 변경하지 않으며 수정·삭제 API를 제공하지 않는다.

### 구축 및 검증

- 데이터 통제 센터에 `감사·변경이력` 탭과 `/api/audit-log` 조회 API를 추가한다.
- 처리자, 시각, 작업, 대상, 사유, 변경 필드와 변경 전후 스냅샷을 한 화면에서 확인한다.
- 전역 최신 조회를 위한 복합 인덱스를 추가하고 관리자 권한, 입력 바인딩, 보안 값 가림, 읽기 전용 통제를 회귀 테스트한다.

## 24. 15차 구축·평가 결과 — 기준정보 위험 주간보고 확인·승인

### 평가

- 기준정보 영향 해결 큐와 주간 스냅샷은 존재했지만, 조직장 응답과 보완조치, 경영 책임자 승인 결과가 하나의 감사 가능한 흐름으로 연결되지 않았다.
- 현재 사용자 권한은 대표 계정 한 명이므로 조직장이 직접 로그인해 확인한 것처럼 기록하면 실제 행위자와 책임자가 뒤섞인다.
- 기존 전자결재의 보완 재제출·기안 취소를 그대로 허용하면 불변 스냅샷이 결재 진행 상태에 남아 운영이 교착될 수 있다.

### 개선된 기획

- 주간 보고 본문과 SHA-256 체크섬은 생성 후 수정할 수 없도록 API와 SQLite 트리거에서 함께 잠근다.
- 조직장별 확인 원장에는 조직장, 실제 기록자, 응답 내용, 처리 시각을 분리해 저장한다.
- 보완이 필요하면 재직자 담당자와 기한을 지정한 후속업무를 통합 업무함에 만들고, 업무가 완료되기 전에는 확인 완료를 차단한다.
- 모든 조직장 확인이 끝난 보고서만 데이터 통제 전자결재에 제출한다. 같은 보고서에는 결재를 하나만 연결한다.
- 불변 보고서는 승인 또는 반려로만 종결한다. 보완이 필요하면 기존 보고서를 고치거나 재제출하지 않고 새 스냅샷 버전을 만든다.
- 동일인 기안·승인이 가능한 현재 권한 구조를 화면에서 숨기지 않고 자동 승인·자동 종결을 사용하지 않는다.

### 구축 및 검증

- `erp_master_impact_weekly_report_reviews`, `erp_master_impact_weekly_report_events` 원장과 보고서 워크플로 상태를 추가한다.
- 데이터 통제 화면에서 조직장 확인, 보완업무 생성, 완료 결과 검증, 경영 책임자 전자결재 제출과 최종 상태를 확인한다.
- 전자결재 센터와 결재선 설정에 데이터 통제 유형을 연결하되 일반 새 기안에서는 이 전용 결재를 만들 수 없게 한다.
- 조직장 중복, 보고서별 결재 중복, 스냅샷 변조, 후속업무 미완료 제출, 불변 보고서 취소·보완 재제출을 회귀 테스트로 검증한다.
# 25. HR 퇴직 효력·월 임금안 연계

- 퇴직 승인과 퇴직일 도래가 고용상태를 결정하고, 정산·회수 완료 여부는 별도의 오프보딩 절차상태로 관리한다.
- 퇴직일이 지난 미완료 건은 `EFFECTIVE`로 두어 조직과 재직 명부에서는 제외하되 입·퇴사 관리에서 계속 처리한다.
- 인사기록의 기본급·식대·육아수당·자가운전수당을 월 임금안의 기준정보로 사용한다.
- 월 임금안은 서버의 월별 초안과 직원별 스냅샷으로 저장하며 확정 시 HR 급여관리의 같은 월 기록을 교체한다.
- 확정본 재개방은 HR 급여가 아직 작성 중일 때만 허용하고, 버전 충돌·항목합계 불일치·중복 월 기록을 차단한다.
- 상세 기획과 검증 기준은 `docs/hr-retirement-compensation-plan.md`를 따른다.
